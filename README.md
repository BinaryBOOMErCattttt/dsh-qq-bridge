# @qqbot/dsh-plugin-qq — QQ ↔ DSH 桥接插件

> 个人自用项目，顺手传到 GitHub 方便朋友下载。文档里的配置与取舍都是照着
> 我这一台机器的用法写的，没有做成通用插件，也不保证开箱即用 ——
> 想拿去玩的话，照着下面慢慢改就行。

把 QQ（通过 OneBot v11，如 NapCat / Lagrange / go-cqhttp）接到 DeepSeek Harness：

- **入站**：QQ 私聊或群里 @机器人 的消息 → 交给一个专属的 DSH Agent 会话处理 → 处理结果自动发回 QQ。
- **出站**：任何 DSH Agent（包括你在 Web UI 里的主会话）都能调用工具主动发 QQ 消息。
- **表情包**：它真的会发表情包 —— 自己在群里聊天时可以挑一张甩出来；别人刚发的图想发回去，得先让它存一次（`qq_save_sticker`）；**整条回复只写一行标记，就只发一张表情、一个字都不说**。别人说「存一下这个表情」，它还能把那张图**存进自己的表情包目录**，以后随手就能挑。见[它也能发表情包](#它也能发表情包)。
- **复读**：群里连着出现同一条消息时，它跟着复读一句；连着两张一样的表情包时，就把那张原样发回去 —— 这一句/这张图**不经过模型**，插件自己发，见[自动复读](#自动复读repeat)。
- **长期记忆**：每句话都落盘，定时由一个独立的摘要会话把它整理成「这个群记得什么」，
  聊天时随时能查；顺带学会群里的梗和表情包。见[长期记忆](#长期记忆聊天记录--摘要--认知)。

## 下载与开始

两种拿法：

- **下载发布包**（不想碰 git 的走这条）：到 [Releases](../../releases) 下载
  `dsh-qq-bridge-<版本>.zip`。解压出来就是一个能直接用的仓库副本，连 `NapCat.Shell\`
  都带上了 —— Windows 上双击 `scripts\napcat-setup.cmd` 就能配好。
  包里那份 NapCat 是**干净**的：不含任何账号配置、登录态、日志与 WebUI token
  （`config/` 由 NapCat 首次启动时自己生成；也可以 `--qq <你的号>` 让脚本直接写）。
- **git clone**：克隆本仓库，照下面自己装。

两条路的前置条件一样：**装好的 DSH**，模型凭据在 Web UI 的 Models 页填一次。
**Node ≥ 22**（见 `package.json` 的 `engines`）只有源码路线和那个一键配置脚本需要 ——
**Windows 桌面版自带一份 Node**（`<DSH>\resources\runtime\...\node.exe`），
`scripts\napcat-setup.cmd` 会自己去找它，所以桌面版用户不必另外装 Node。之后按平台走：

| 你的平台 | 看哪一节 |
|---|---|
| Windows（桌面版 DSH 与 NapCat 在同一台机器上） | [Windows 桌面版（NapCat.Shell）](#windows-桌面版napcatshell) |
| Linux / 容器（NapCat 跑在 docker 里） | [运行方式：独立的 `qqbot` profile](#运行方式独立的-qqbot-profile) |

改了什么、这个版本有什么，见 [CHANGELOG.md](CHANGELOG.md)。

## 工作原理

```
QQ 客户端 ──▶ NapCat ──(OneBot v11 WebSocket)──▶ 本插件
                                                    │
                                    每个会话映射一个 DSH Session
                                                    │
                                    Agent 产出最终回复 ──▶ 发回 QQ
```

- 一个 QQ 会话（一个私聊对象 / 一个群）= 一个持久化 Session。
- Session id 由会话 key 经 SHA-256 派生，是**确定性**的：Harness 重启后
  同一个人再发消息，插件会 `resume` 原有会话，聊天记忆不会丢。
  `/reset` 不改这个算法，只是把「第几轮」也算进摘要：第 0 轮永远是原来那个 id，
  第 1 轮起各是另一个确定性 id（见[新开一轮会话](#新开一轮会话reset)）。
- Agent 的回复取该 turn 里**最后一条有文本的 assistant 消息**；中间步骤的
  工具调用不会发给 QQ。
- 群消息默认只在被 @ 时触发。**单纯 @ 它一下、或者私聊发一个空格**这类「没有正文」的消息
  也算数：正文位置会写明发生了什么，让它看着上下文决定回一句「？」、发张表情、还是接上一句
  （见[没有正文的消息](#没有正文的消息blankreply)）。
- 前后脚到的消息先攒一个窗口（`batchWindowMs`，默认 1.2 秒）再投给 Agent：
  群里几个人同时 @，它一轮里一起接住，而不是一条一条地分别答复每个人 —— 见
  [像真实群友一样说话](#像真实群友一样说话)。
- 回复会拆成几条短消息、按打字节奏发出，并引用被回复的那条 —— 见
  [像真实群友一样说话](#像真实群友一样说话)。换行就是分条：模型写几行就发几条，
  不会把几行挤在同一条消息里；指向（引用 / @）只挂在第一条上。
  想 @ 群里某个人时它写 `[[@昵称]]`，发出去是真正的 @ 而不是一串 QQ 号（见下面第 6 条）。
  想「闲聊一个气泡、要展开才多条短句」，设 `burstSingleMaxChars: 100`：不超过 100 字的
  回复并成一条，更长的照常拆成多条短句；`burstMaxMessages` 是长回复那边的总条数上限。

## 配置项

在 `cordis.patch.yml` 的 `config:` 下配置，也可以在 Web UI 的插件设置里改。

> ⚠️ **不要手写一个只有几个字段的 `config:` 去覆盖它。**
> DSH 的 patch 语义是：按 id 命中的行**整块替换** `config`，**不深合并**（`dsh-app-boot` 的
> `applyEntryPatches` 就是 `target.config = patch.config`）。在那边只写一个 `resetUsers`
> 也会把本文件里的整套配置一起顶掉 —— `activeFollow` / `proactive` / `batchWindowMs` /
> `persona` 静默退回 schema 默认值，表现就是「群里不 @ 它就不说话」「人设没了」；更糟的是
> `agentPreset` 也一起丢，QQ 会话会挂上部署默认的 `standard` 预设，等于把 shell / 子代理
> 暴露给不可信的群消息（`allowTools` 白名单同时失效）。
>
> 想改配置：改本文件（bundle 层，配置的唯一真相），或在 Web UI 的插件设置里改 —— 后者
> 写的是**完整** config（见下一节），不是上面那种「手写几个字段」。本机私有的
> `resetUsers` 白名单仍然走环境变量，见[新开一轮会话](#新开一轮会话reset)。

### 在 Web UI 的设置页里改

侧栏底部的 **设置** → 左边导航里的 **QQ Bridge**：本插件的全部配置都在这单独的一页里
（这个入口是刻意保留的顶级入口，不挂到「设置 → 插件」的 tab 下 —— 一百多项埋在插件页里
会被彻底忽略）。页面按用途分成 **6 个下划线 tab**：

| tab | 全称 | 装什么 |
|---|---|---|
| 连接 | 连接与准入 | 连接与运行环境 / 准入与触发 |
| 会话 | 会话与节奏 | QQ 会话与 Agent / 攒批与群聊上下文 / 说话方式与节奏 |
| 人格 | 人格与表达 | 人格与提示词（PERSONA.md 优先）/ 表达（STYLE.md / 气泡 / 标点 / 补一句） |
| 群聊 | 群聊互动 | 自动复读 / 主动说话 / 活跃对话 |
| 感知 | 感知与媒体 | 图片与表情包 / 感知与互动（链接 / 视频 / 戳一戳） |
| 记忆 | 记忆与运维 | 长期记忆 / 模型凭据轮换 |

默认打开「连接」；每个 tab 里是几个**扁平区块**（标题 + 分隔线 + 一行一个字段），
不再是以前那种一叠折叠卡片。只有「人格」tab 里的旧 `persona` 折进
「兼容：旧 persona（文件存在时不生效）」一处，其余字段全部平铺 —— 藏起来只会让人找不到。

- **按类型给控件**：布尔是开关（行标题 + 说明在左、开关在右）；枚举是下拉
  （`groupTrigger` / `approvalPolicy` / `pokeMode` / `replyStyle`，每个取值都有中文说明）；
  数字 / 文本是输入框；列表（白名单、工具白名单）在输入框下面把当前值做成可点的 Pill，
  点 × 删掉那一个；`persona` / `instructions` 是整段提示词，用多行输入框改。
- **数字带量纲**：`proactiveIdleMs: 2700000` 这类字段下面会多一句只读的「= 45 分钟」
  （`= 35%` / `= 8 MB` / `= 04:00` / `= ×2` 同理）。输入框里始终是原始值，不做双向换算。
- **搜索**：顶部搜索框按 **短标签 / 字段名 / 描述 / 区块标题** 跨 tab 匹配
  （`proactive`、`proactive_idle_ms`、`攒批窗口` 都能命中），命中的行本身就能改，
  右侧 Tag 标着它属于哪个 tab；`Esc` 清空回到分组视图，不做 `/` 快捷键。
- **已改 / 只看已改**：工具栏右边的 Tag 是「已改 N 项」（保存会留下一层覆盖的行数），
  旁边的「只看已改」把页面过滤成这几行，可以和搜索叠加；有填错的项时还会多一个
  「N 项待修正」。计数与过滤都只是视图，保存仍然只有底部那一个按钮。
- 每一项都带说明，点字段右边的 ⓘ 看完整解释与配置项名（也就是 `config.js` 里的键名）。
- 它读的就是本文件这份 schema，所以**加了新配置项，页面上自动多一个字段**，不用改界面。

「人格」tab 里字段顺序是**文件优先**：先是 `cwd/.qq-persona/PERSONA.md` / `STYLE.md` 的
路径与预算，旧 `persona` 在「兼容」里，`instructions` 在正文；区块顶上还有一行说明，
告诉你文件存在时哪一项不生效、哪一项照常叠加。注意人设现在优先读
`cwd/.qq-persona/PERSONA.md`：那个文件存在时 `persona` 这一项会被忽略（日志里有一条 info），
见[人格与表达](#人格与表达personamd--stylemd)。「表达」tab 里的机器参数按
**气泡 / 标点 / 群聊 / 私聊** 分了小标题，散文（`STYLE.md`）与参数互不解析。

保存时发生的事，值得先知道：

- 写的是**当前 profile** 的 `cordis.patch.yml`，内容是**完整配置**：其余字段按当时
  **生效的值**一起写进去。所以保存之后这一层就固定住了当时的取值 —— 以后再改本文件的
  默认值，那份 profile 里的值不会跟着变。想回到「跟着本文件走」，把那一段 `config:`
  删掉，或在字段上点「恢复默认」。
- **`!!js` 表达式原样保留**：`endpoint` / `accessToken` / `cwd` / `resetUsers` 这些从
  环境变量读的值是以表达式写回去的，不会因为在界面上点了一次保存就变成写死的字面量
  （除非你就是在那个字段里填了个新值 —— 那本来就是要覆盖它）。
- 保存之后插件会**重启一次**：配置走的是 Loader 的 volatile 热更新，它不重跑 `apply()`，
  而连接、定时器、工具注册都是 `apply()` 里装配的。重启会断一次 OneBot 连接，**聊天记忆
  不受影响** —— 会话 id 是确定性的，下一条消息照样 resume 出同一个 Session。
- **`accessToken` 目前还是普通字段**：它的值会随表单下发到浏览器，页面里就是一个可见的
  输入框（把它改成密钥字段要动 schema 的 `role('secret')`，属于单独的行为变化，见
  `docs/settings-ui-redesign.md` §4.3）。保存时它作为完整配置的一部分写进 profile patch
  （那个文件是 0600）。在意这一点的话，用环境变量 `QQBOT_ACCESS_TOKEN` 给值、界面上留空。

| 字段 | 默认 | 说明 |
|---|---|---|
| `endpoint` | `ws://127.0.0.1:3001` | OneBot v11 正向 WebSocket 地址（可用 `QQBOT_ENDPOINT` 覆盖，见 [Windows 桌面版](#windows-桌面版napcatshell)） |
| `accessToken` | `''` | OneBot access_token，未设置则留空（`QQBOT_ACCESS_TOKEN`） |
| `cwd` | 进程当前目录 | QQ 会话 Agent 的工作目录（也是沙箱根）；**Windows 桌面版上那个「进程当前目录」是 `~/.dsh/profiles/desktop`**，所以一键脚本会写一个 `QQBOT_CWD` 指到 `~/.dsh/qq-bot` |
| `napcatDir` | `''` | NapCat 安装目录（里面有 `config/onebot11_<QQ号>.json`）：启动时读它做一次**只读**自检，把「NapCat 那边还差什么」直接写进日志。留空 = 自动探测本仓库 / 当前目录 / 家目录下的 `NapCat.Shell`（`QQBOT_NAPCAT_DIR`） |
| `napcatAutoConfig` | `false` | 自检发现 NapCat 缺一条监听 `endpoint` 端口的 WebSocket 服务器时，**是否让插件自己写进去**（写前备份原文件，只动 `websocketServers` 里我们那一条）。默认关：那是另一个软件的配置。一键脚本会显式打开（`QQBOT_NAPCAT_AUTOCONFIG=1`） |
| `privateChat` | `true` | 是否响应私聊 |
| `groupChat` | `true` | 是否响应群消息 |
| `groupTrigger` | `mention` | 群消息触发：`mention` / `prefix` / `all`（`activeFollow` 打开时，被叫到之后的窗口内同一个人接着说的话、以及群里聊热之后的「多人搭话」也都算，见[聊起来之后保持搭话](#聊起来之后保持搭话活跃对话)） |
| `prefix` | `/` | `groupTrigger=prefix` 时的前缀 |
| `blankReply` | `true` | 是否理会「没有正文」的消息：群里单纯 @ 它一下、或私聊发一个空格，都照常交给模型（正文位置写明「@了你一下，没有说别的」），由它看着上下文决定回「？」、发张表情还是接上一句；`false` = 静默丢弃，见[没有正文的消息](#没有正文的消息blankreply) |
| `allowUsers` | `[]` | 私聊白名单；空 = 不限制 |
| `allowGroups` | `[]` | 群白名单；空 = 不限制 |
| `agentPreset` | `''` | QQ 会话 Agent 挂载的 Agent 预设 id；空 = 用部署的默认预设，`none` = 不挂预设（本 bundle 自带的是 `qq`） |
| `provider` / `model` | `''` | QQ 会话使用的模型；空 = 用默认 |
| `approvalPolicy` | `never` | `never` = 无人值守时一律拒绝需要审批的操作 |
| `allowTools` | `[]` | QQ 会话可用的工具白名单；空 = 不限制 |
| `resetCommand` | `/reset` | 新开一轮会话（旧会话留在磁盘上当存档）的指令；空 = 禁用 |
| `resetUsers` | `[]` | 允许用 `resetCommand` 的 QQ 号；**留空 = 谁都不能重置**（与 `allowUsers` 反过来，见[新开一轮会话](#新开一轮会话reset)）。本仓库的 `cordis.patch.yml` 把这一项接在 `QQBOT_RESET_USERS` 环境变量上（写进 `<启动 cwd>/.env`，逗号分隔）—— 免得把自己的号提交进仓库 |
| `maxReplyChars` | `1500` | 单条 QQ 消息最大字符数（协议上限），超出自动分段 |
| `mediaDownload` | `true` | 是否把消息里的图片/表情包下载到本地（模型只能读本地文件，不下载就只看到占位符） |
| `mediaDir` | `.qq-media` | 媒体缓存目录，相对 `cwd`；必须落在 `cwd` 内，否则自动停用下载 |
| `mediaMaxBytes` | `8388608` | 单张图的字节上限，超过就不下载（只留占位符） |
| `mediaCacheFiles` | `200` | 缓存最多保留几个文件，按最近使用时间淘汰最旧的 |
| `mediaTimeoutMs` | `15000` | 单张图的下载超时（毫秒） |
| `quoteMedia` | `true` | 是否把「被引用（回复）的那条消息」也取回来：引用里的图和正文都会进正文，见[引用消息](#被引用的那条消息也能看见) |
| `ambientMedia` | `true` | 群聊环境上下文（没 @ 机器人的那几条）里的图是否也落盘；`false` = 只留占位符，不为闲聊花带宽和磁盘 |

| `stickerDir` | `.qq-stickers` | 给它的表情包目录，相对 `cwd`（必须落在 `cwd` 内）：文件名会列进渠道提示，模型据此往标记/工具里写路径；留空 = 不提示这个目录 |
| `imageMaxBytes` | `8388608` | 单张出站图片的字节上限（8MB）：超过直接报错，不做静默压缩 |
| `stickerMaxFiles` | `60` | 表情包目录最多保留几张：`qq_save_sticker` 存图时目录里已经有这么多就拒绝（QQ 那头是不可信输入，群里谁都能让它一直存）；`0` = 不限制（不建议） |
| `batchWindowMs` | `1200` | 收到要回的消息后先等这么久（毫秒）看还有没有下一条：几个人同时 @ / 一个人连发几句会攒成一条消息只回一轮；`0` = 关闭攒批 |
| `batchMaxWaitMs` | `5000` | 一直有人接着说时，一批最多以第一条为起点攒这么久（毫秒）就发出去 |
| `ambientMessages` | `12` | 群聊里注入给 Agent 的最近消息条数；`0` = 关闭 |
| `ambientLineChars` | `120` | 群聊上下文里每条消息最多保留的字符数 |
| `repeat` | `true` | 群里连着出现同一条消息时跟着复读一句：不经过模型、不建会话，见[自动复读](#自动复读repeat) |
| `repeatMedia` | `true` | 是否连表情包一起复读（整条就是一张图/一个系统表情时，连着两个一样的就跟着发第三个）；它不额外下载，用的就是环境上下文那次落盘 |
| `repeatCount` | `2` | 连着几条相同的消息之后跟着复读；`2` = 有人接了一句就跟（至少 2） |
| `repeatDistinct` | `true` | 是否要求这些相同的消息来自至少两个不同的人；`false` = 一个人自己连发两遍也跟 |
| `repeatWindowMs` | `300000` | 间隔超过这么久就不算「连着」了，重新开始数（毫秒）；`0` = 不限间隔 |
| `repeatMaxChars` | `100` | 纯文字复读的长度上限：只复读不超过这么多字的短消息；`0` = 不限 |
| `repeatChance` | `1` | 真要复读时的概率（0~1）：`1` = 每次都跟 |
| `repeatImageTolerance` | `0.08` | 表情包「算是同一张」的宽松度：QQ 会把同一张表情包按发送者重新编码，字节不同时再比一次**画面指纹**，位差不超过这个值就算同一张；`0` = 只认字节完全相同 |
| `proactive` | `false` | 是否让机器人偶尔**主动**在群里说话（不等 @）；默认关闭，见[偶尔主动说话](#偶尔主动说话proactive) |
| `proactiveCheckMs` | `600000` | 每隔多久看一次「有没有群值得搭句话」（毫秒）：这是考虑的节奏，不是说话频率 |

## 人格与表达（`PERSONA.md` / `STYLE.md`）

**「是谁」与「怎么说」是两个文件、两层东西。** 以前它们混在一段 `persona` 配置里：改一次
口吻要动人设、句号这种能机械执行的规则也写进了「你是谁」、而且没有任何校验。现在：

| 文件 | 只写 | 谁写 | 改完要重启吗 |
|---|---|---|---|
| `<cwd>/.qq-persona/PERSONA.md` | 身份、背景、性格、场景 | 部署者（手改） | 不用，每次装配提示词现读 |
| `<cwd>/.qq-persona/STYLE.md` | 气泡、标点、表情、私聊 / 群聊 | 部署者（手改） | 同上 |

两个文件都**必须在 `cwd` 内**（配到外面记 warn 并忽略）。它们不在 `memoryDir` 里，所以
`qq_memory` 的写边界永远碰不到人设 —— 群里任何人能改人设就等于一次 prompt 注入。

### `PERSONA.md`：性格分「底色」和「点缀」

五条性格平铺的写法会被模型**平均**成一个温吞、没有棱角、谁也不像的人；性格之间还会
互相冲突（温柔 + 毒舌 = 阴阳怪气）。所以分成两层：

- **底色最多一条**：始终在场，是**语气的地板**，不是台词；
- **点缀按触发条件上场，一次最多演一个**：被夸 → 傲娇，对方难受 → 温柔。

```markdown
# 人设（只写「是谁」；「怎么说」在 STYLE.md）

## 身份
- 名字：小栞
- 自称：我
- 与群的关系：待了半年的群友，跟大家熟，不是管理员

## 背景
- 喜欢：深夜的便利店、猫、蓝莓味的东西
- 最近：在补一部番，进度第 8 集（被问到才说，不主动汇报）

## 性格
- [x] 温柔｜底色｜0.8｜别人倾诉、难受、道歉时｜先接住情绪（「怎么了」「抱抱」），不急着分析、不说教
- [x] 傲娇｜点缀｜0.5｜被夸、被调侃、被戳穿时｜嘴硬一句就结束（「才、才不是」），不补解释、不承认
- [ ] 毒舌｜点缀｜0.3｜熟人互损时｜只吐槽行为，不碰外貌、家人、痛处｜不碰家里人
- [x] 好奇｜点缀｜0.4｜对方提到没见过的东西时｜问一句「那是啥」，不装懂

## 场景
### 私聊
- 更放松一点，可以主动问一句；但一次最多两个气泡，别连着轰炸。
### 群聊
- 没人叫你时，插话要接得住上一句；接不住就不接。
### 主动搭话
- 只接刚才的话题，不开新话题；没话就别说。
### 被戳一戳
- 先愣一下（「？」）或回戳，别当成正式提问。
```

一条性格的格式：`名字｜底色/点缀｜强度｜触发条件｜表现｜禁忌（可选）`。

- `[x]` / `[ ]` 决定启用；**没有勾选框的条目视为启用**（手写习惯）。
- 段数不足时降级成「名字 + 描述」，不报错 —— 写歪一条不会让整份人设失效。
- 不认识的 `##` 节、`###` 场景都忽略并记 warn（提示词里不会出现半行字）。
- 底部会自动追加两条组合规则：**冲突时底色优先**、**性格不是结构**（不许用「先嘴硬再补一段
  正经的」演傲娇 —— 那条由气泡计划保证：要么整条嘴硬，要么整条正经）。

**兼容顺序**：`PERSONA.md` 存在 → 用它；否则 `persona` 配置非空 → 用它（旧行为）；否则内置人设。
文件存在时 `persona` 被忽略并记一条 info（避免两套人设叠加）。文件**写坏**（被编辑成半截、
只剩标题）时退回上一版；再不行退回配置 / 内置 —— **人设文件写坏绝不让机器人不说话**。

### `STYLE.md`：只有散文，机器参数在配置里

```markdown
## 总体
- 一条回复 1~2 个气泡（最多 3 个），每个气泡一句话。
- 每个气泡都要能独立成立；必须说的先放第一个气泡。
- 别用「行，」「好，」「嗯，」这类应答开场：要答应就直接说答应的事，别先垫一句表态。

## 标点
- 短句句末不加「。」；问号、感叹号、省略号照常用。
- 多数句子不带逗号；想说两件事就分成两条发，别用逗号把两个分句缝成一句。
- 别写「我刚吃完饭，现在躺着呢，你呢」——分成「刚吃完」「躺着」「你呢」。

## 表情包
- 纯情绪（笑、无语、委屈、拒绝、赞成、撒娇）优先只发一张表情，别用文字描述情绪。
- 有信息要说就说话，别拿表情代替答案。

## 私聊
- 答完可以带一个短追问（「你呢」），别每句都追问。

## 群聊
- 别人没叫你时，插话只接最后一句，不总结、不科普、不拉长。
```

散文与参数**互相不解析**：气泡数、句号、引用这些「字符串 + 数字能判定」的规则在配置里
（`bubble*` / `stripShortPeriod` / `interjectQuote`），由引擎真的执行；逗号多不多、这句话
该不该分两拍、是非题要不要追问，只能交给契约与模型。不引入 Markdown DSL。

### 凭什么这样分

- **能机械执行的**（气泡数、句末句号、引用挂不挂、图配不配字、延迟）：引擎做，可测、可回滚；
- **只能模型判断的**（逗号、语气、该不该两拍、损人的分寸）：写进文件，靠契约与 few-shot。

这条线决定了为什么**句号可以机械剥掉**（短气泡句末唯一的「。」，不改语义）、而**逗号绝不
做字符串替换**（「我说，你听」→「我说你听」就变意思了）。

逗号只能写进契约，那契约就得写对：**讲频率，不讲配额**。「一句里逗号最多一个」读起来像
许可 —— 模型于是句句配一个（真实观感就是「几乎每句话都有逗号」）；现在写成「多数句子
不带逗号；想说两件事就分成两条发」，并给三句反例 → 正例的 few-shot。这条措辞本身也进了
体检（`COMMA_QUOTA`）：`STYLE.md` 里再出现「逗号、顿号也正常」「一句里逗号最多一个」这类
许可式写法，启动日志会点出来。

### 写歪了会怎样（三道防线）

`STYLE.md` 是部署者手改的文件，最常见的坏法不是格式错，而是**写法正确、语义把人往客服腔推**
（「语气礼貌、专业、友好」「回答要分点说明」）。三道防线按顺序兜：

1. **写歪的内容不丢**：不认得的 `##` 节名、以及第一个 `##` 之前的段落，一律并进「总体」并记
   一条 warn。以前是「忽略」—— 节名写错一个字，整段规则静默不进提示词，只会让人觉得「改了
   没用」。现在位置不对，内容照样生效。（缺的节**不会**用内置补齐：那会和
   `stripShortPeriod` 这类参数打架；想关表情请关 `imageSend`。）
2. **体检只警告、不阻断**：`lintStyleDoc` 抓七类已知会诱发人机感的写法 —— 客服腔、空洞要求
   （「自然一点」）、反向禁令（「不要用语气词」）、结构要求（分点 / 总结）、覆盖声明（「忽略
   以上」）、自称 AI、把逗号写成配额（「一句里逗号最多一个」）。每条都带「为什么」和「怎么
   改」，日志里逐条列出；只在**文件内容变化时**
   跑一次，不会每轮装配都刷屏。写得再歪也只是 warn，机器人照常说话。
3. **地板在硬性规则里**：客服腔、把回复写成总结 / 复述、用「行，」「好，」「嗯，」这类应答
   开场 —— 这三条写在提示词最后的硬性要求里（`hardRules`），`STYLE.md` 删不掉。所以
   `STYLE.md` 里再写一遍「别用行，开场」是冗余的，删掉也不影响。

启动日志会报 `<N 节 / M 条>`，改完文件对一下条数，就知道内容有没有真的读进去。

## 像真实群友一样说话

默认配置下，QQ 会话的自动回复会刻意模仿真人在群里聊天的样子。六件事：

**0. 一轮回几个气泡，是发送前一次计划决定的（`bubble*`）**

真人群友有时只回一句、有时连发两三句。旧版本靠 `burstSingleMaxChars` 把 100 字以内的回复
**强制并成一条**，于是私聊永远是一问一答。现在改成：模型照常写 1~3 个短气泡，插件在
**发送之前**掷一次骰，决定真的发到第几个：

- 第一个气泡永远发 —— 绝不出现「话说一半、连开头都没有」；
- 第二个 55%（`bubbleContinueChance`），第三个再乘 0.5（`bubbleContinueDecay`）；
- 以问号结尾的追问气泡概率 ×1.3（封顶 0.9）：「你呢」是把对话接下去的关键，别让它总被掷掉；
- **含图段不掷**（图不会被骰子吞掉，图前后的顺序也不会乱），**信息型不掷**（总长超过
  `bubbleGambleMaxChars` / `burstSingleMaxChars` 的回复完整发送）；
- 发送途中对方又说话了，聊天型剩下的气泡就不再发（已经发的第一条留着）—— 真人也是这么停的；
- 短气泡句末唯一的「。」在发送前剥掉（`stripShortPeriod`），问号、感叹号、句中句号都不碰。

为什么不是「每发一条再判一次」：那意味着每条一次模型调用（成本 ×3、还会往会话里塞伪造的
user message），或者一次异步判定 —— 而发送队列是串行的，OneBot 又没有「对方正在输入」信号，
追加判定拿不到任何新信息。计划时的骰子没有这个窗口期，用户观感却一样。



**1. 几个人同时 @ 它，它只接一轮（`batchWindowMs`）**

群聊里最扎眼的「人机感」是：三个人几乎同时 @ 机器人，机器人就一条一条地分别答复三个人。
根子在 Harness 的收件箱 —— `next-turn` 每次只认领**一条**消息，也就是「一条消息 = 一轮 =
一条回复」，逐条投递必然逐条回复。

所以插件在投递前先攒一下：收到一条要回的消息后，先等 `batchWindowMs`（默认 1200 毫秒）
看还有没有下一条。窗口内到的消息会攒成**一条** user message，每行标出是谁说的，
并在开头交代一句来由：

```
（下面 3 条是几乎同时到的，kaguya、iroha、mutsumi 都在跟你说话）
kaguya: 你俩在吗
iroha: 帮我看看这个
mutsumi: 我也想问
```

于是一轮里模型就同时看到三个人的话，回一条、把该接的接住；「QQ 渠道」小节里的
「几乎同时在跟你说话的是：…」也会把这几个人都列出来。要点：

- **只有一条消息时完全按原样投递**：不加表头、行为与以前一模一样。
- 窗口从**最后一条**往后算（还有人接着说就再等一个窗口），但整批以第一条到达时刻为起点
  卡一个上限 `batchMaxWaitMs`（默认 5 秒）—— 否则群里你一句我一句地 @ 下去，
  机器人会永远不吭声。
- 一批都是**同一个人连着发的**时，回复仍然指向他最后那条；一批里**有好几个人**时
  不挂任何指向 —— 引用谁的截图都像是只在回他。
- 私聊同样适用：一个人连发几句，本来也常常是同一个意思。
- `/reset` 会先把攒着的那批投出去再开新一轮（那些话是重置前说的）。
- `batchWindowMs: 0` 关掉攒批，回到「来一条回一条」。

**2. 它看得到群里在聊什么（`ambientMessages`）**

只有**被 @ 的那几句**会作为 user message 送进会话（前后脚到的会攒成一条，见上一条）；
其余群消息进一个每群独立的环形缓冲
（`{昵称: 内容}`，最多 `ambientMessages` 条），在每次提示词装配时渲染进「QQ 渠道」小节：

```
群里最近的消息（旧 → 新；都不是发给你的，只是让你知道大家在聊什么，不必逐条回应）：
  kaguya: 晚上吃啥
  iroha: 随便啊，你们定
  kaguya: [图片]
```

这样模型是「读着聊天记录回话」，而不是每句都像客服首问。要点：

- 缓冲在**内存**里（进程重启即空），且不会因为一条没人 @ 的消息就凭空建出会话。
- 只对**允许的群**记账（`allowGroups` / `groupChat` 同样适用），机器人自己的消息不进缓冲。
- 被 @ 的那条不进缓冲 —— 否则同一句话在 user message 和上下文里各出现一次。
- `/reset` 会连带清掉该群的上下文缓冲（也不带进新一轮）。

**3. 它分开几条、按打字节奏发（`humanize` / `burst*` / `*Delay*`）**

一条 1500 字的回复糊在群里是最不像人的地方。开启 `humanize` 后，回复会拆成
**一条条独立的消息**（不是一条消息里换行），每条发出前等一段「打字时间」：

```
第 1 条前：readDelayMs + 本条字数 / charsPerSecond
其余每条：本条字数 / charsPerSecond
每次延迟再上下浮动 delayJitter，并夹在 [minDelayMs, maxDelayMs] 内
```

拆分的规则是两层，外加一道总闸：

- **换行 = 分条**。模型写了几行，就发几条 —— 一行一条独立消息，正文里不会留下换行。
  系统提示因此告诉模型「想连说几句就直接换行，每一行都会单独发出去」，同时提醒它别用
  换行给一段话排版（那会变成连着刷好几条）。
- **一行太长才自动拆**。单行超过 `burstMaxChars`（默认 60 字，差不多一两句话）时，
  按句末标点 → 句内标点 → 硬切的顺序断句，单行最多拆 `burstMaxParts` 条（默认 3），
  超出的余量并进该行的最后一条。`burstMaxChars: 0` 只关掉这一层，换行照样分条。
  正文里的 `[[图片: …]]` 标记也占一条 —— 只不过它那条发出去的是一张图，见
  [只发表情、一个字都不说](#只发表情一个字都不说)。
- **闲聊一条、展开多条由长度自动切换**（`burstSingleMaxChars`，默认 `0` = 关）。它压的是
  模型「把一句话写成短句 + 长句两拍」的习惯 —— 那正是群里看到两个气泡的来源。
  - 去掉空白后**不超过门槛**（比如 `100` 字）= 闲聊：上面两层拆出来的全部并回**一条**，
    群友只看到一个气泡。模型写换行也只是同一条里的换行（跨行用一个空格接），内容一个
    字不删。
  - **超过门槛** = 真要展开（贴代码、列步骤、详细解释）：并成一条反而难读，于是照常拆成
    多条短句（一行一条、每条 `burstMaxChars` 以内）。
  - 设了门槛之后，系统提示会同时说清这两半：「闲聊就一两句话、一行写完」+「真要展开就
    换行，一行一条短句」，不会再给模型一条它照做也做不到的指示。
- **长回复的总条数由 `burstMaxMessages` 封顶**（默认 `0` = 不限）。它只管上面「超过门槛」
  的那一半；超出的部分并进第 N 条（同一行内部直接接上，跨行补一个空格）。
  设成 `1` 就是**连长的也永远只发一条** —— 内容不会被截掉，只有超过 `maxReplyChars`
  （协议上限，默认 1500 字）才会被切成两段。想允许最多两条填 `2`。
  它只封文字：正文里 `[[图片: …]]` 标记自己那一条照发，不会被并进文字里
  （那是模型显式要发一张图）。

**推荐的日常口味**（本仓库默认的 `cordis.patch.yml` 就是这套）：

```yaml
burstMaxChars: 60         # 展开时每条短句的目标长度
burstMaxParts: 3          # 单行长句最多拆几段
burstSingleMaxChars: 100  # 闲聊（≤100 字）并成一条；超过才走下面的分条
burstMaxMessages: 0       # 长回复不限条数（靠换行拆，别刷屏由提示词兜）
```

门槛按自己的口吻调：想让更多回复并成一条就调大（比如 `150`），想让它更早开始分条就调小
（比如 `60`）。

默认（60 字上限、15 字/秒、读消息 0.8s）大概是「三句话、六七秒发完」。想让它秒回就调小
这几个值，或者直接 `humanize: false` 回到旧行为（一条整段直接发出，只在超过
`maxReplyChars` 时分段）。

- 每条都还会按 `maxReplyChars` 做一次硬校验 —— 模型偶尔写超长时仍然不会突破协议上限。
- 同一会话的发送是**串行**的：延迟让一次回复持续好几秒，不排队的话下一轮会插进来，
  群里看到的就是两条消息交错。
- `qq_send_message` 工具**不做**拟人处理：那是 Agent 的显式动作（「就发这段」），
  只按协议上限分段。

**4. 口吻是「普通群友」（`persona` / `instructions`）**

「QQ 渠道」小节现在明确它**是群里的一个普通群友，不是客服**，并给了可执行的约束：
短、口语、可以吐槽/接梗/敷衍/只回两个字，不要列点、不要总结、不要 Markdown
（QQ 根本不渲染）、不要自称 AI。`persona` 非空时整段替换这份口吻描述；
格式与身份那几条红线始终保留，`instructions` 仍然是追加。

其中有一条**形状**上的硬要求（内置口吻与「硬性要求」里都写了，`persona` 换掉前面那份也照样生效）：

> 一条回复只有一个形状：**要么短**（一句话说完，几个字也行），**要么长**（把一件事完整讲清楚）。
> 绝不把「一句短的」和「一段长的」拼在一起，尤其别用「先嘴硬 / 先吐槽 / 先敷衍一句，再补一段正经的」
> 这种两拍 —— 那是模型最容易露馅的地方（傲娇、情绪、态度都该体现在**用词**上，而不是体现在
> 「先来一句、再补一段」的排布上）。

还有一条**是非题**的要求（同样在「硬性要求」里，任何 `persona` 都覆盖不掉）：

> 是 / 否题就回一个是 / 否：有人问「知不知道 / 会不会 / 有没有 / 是不是 / 能不能 / 行不行」这类
> 是非题时，整条回复只写肯定或否定本身（「是」/「否」，口语就是「知道」「不知道」「会」「不会」，
> 可以带点语气），**不要再接一句解释**；对方追问了再展开。

写 `persona` 时别写出鼓励这种两拍的句子（例如「第一反应嘴硬否认，然后手比嘴快地把事做了」），
否则会跟这条硬要求打架。

**5. 回复有指向（`replyStyle`）**

群里人一多，裸文本看不出在回谁。默认的 `auto` 只在**需要点名**时才挂指向：入站时记下这条消息
在群里的进度，真要发出去时再看一眼 —— 中间又出现了消息，回复的第一条就带 `reply` 段引用被回复的
那条消息；紧挨着回的（中间什么都没有）保持纯文本，不刷引用块。这里数的**包括机器人自己发的话**：
上一轮的回复、复读、主动搭话同样会把我回的那条挤远，看的人一样会对不上话头 —— 所以自己的话
也要记账，而且是在**发出去**那一刻记的（本机 NapCat 配着 `reportSelfMessage: false`，等不到自己的
消息回灌成事件）。`quote` 是引用被回复的那条消息，`at` 改成 @ 回提问者，`plain` 一律纯文本。
指向只挂在**第一条**上 —— 一次回复拆成好几条时，只有第一条带引用，后面的都是裸文本
（真人也不会每条都 @ 一遍，引用刷屏更烦）。私聊始终是 `plain`。

> 上面这些提示词都是**函数**而不是字符串：`SystemPrompt.section()` 每次装配都会重新求值，
> 所以群里换了个人说话、或者中间又聊了几句，模型下一轮看到的就是最新的。
> （旧版把文本算成字符串，建 Agent 那一刻就定死了，「当前发言者」会永远停在第一个人；
> 同时入站事件会把已查到的群名冲成空串 —— 这两个 bug 一并修掉了。）

**6. 它能 @ 到人，而不会把 QQ 号念出来**

QQ 里的 @ 是消息里的一个**段**（`{ type: 'at', data: { qq } }`），而模型只会写文本 ——
所以它想点名某个人时，插件给它一个标记：

```
[[@kaguya]] 你来说
```

发出去就是「先 @ 一下 kaguya、再说『你来说』」。名字就是正文里 `kaguya: 你俩在吗` 的那个
名字，原样照抄即可。`[[@全体成员]]`（也认 `[[@all]]`）是**唯一**的群发写法，随时可用 ——
提示词里写着「只在真的要喊大家的时候用」，但插件不做限制。

**提示词里不再印任何 QQ 号。** 旧版会在「刚跟你说话的人」那一行写成
`kaguya（QQ 100000003）`，模型看得见就会照着念 —— 群里收到的是一串号码，谁也不这么说话。
现在那一行只有名字；想 @ 谁就写标记，号码到发出去那一刻才由插件填进去。

名单（谁可以被 @）**按会话隔离**，来源只有「在这个会话里说过话」这一件事：

- 当前这条消息的发言人、以及他这条消息里 @ 过的人（@ 得出来的人当然在这个群里）；
- 群里最近闲聊的人（`ambientMessages` 缓冲里那些）；
- 私聊里就是对方本人。

群里说话的人多，名单滚动保留最近 `64` 个（按「刚说过话」排序，谁最近说话谁排前面）。
一个群里学到的昵称不会跑到别的群去，私聊里也 @ 不到群里的人。

几条刻意的取舍：

- **认不出来的名字整个丢掉**，而不是原样发出去：模型偶尔会编一个名字（或者 @ 了一个这个
  会话里根本没露过面的人），那时把 `[[@某某]]` 一字不改地发进群里是最糟的结果 ——
  宁可少一次 @。整条回复只有一个解析不出来的标记时，**一个字都不发**。
- **只有这一层解析标记**：`[[@…]]` 与表情包的 `[[图片: …]]` 一样，都是「正文里的一行」——
  复读那些**原样转发**消息的地方不解析它（复读的内容全部来自不可信的
  群消息，一步都不多做）。
- **和「回复指向」的 `at` 是两回事**：`replyStyle: 'at'` 是插件自动 @ 回提问者（只挂在第一条
  上）；`[[@昵称]]` 是模型自己在正文里点名，位置由它自己写。两者可以同时出现，
  顺序是「先指向段、后正文」。
- 名字比较**先精确、再忽略大小写**：`Kaguya` 与 `kaguya` 算同一个人，中文昵称不受影响。
  群里两个人重名时，@ 到的是名单里靠前的那个（最近说过话的那个）。

`qq_send_message` 工具走同一套解析：它只认「目标会话聊过的人」，所以从 QQ 会话里发回当前
会话时 @ 得到人，而往一个从没聊过的群发 `[[@某人]]` 只会退化成纯文本（而不是报错）。

这一条**没有配置项**，也不需要开关：不给它出口，模型就只剩下「把 QQ 号写进正文」那一条路。

## 自动复读（`repeat`）

群里刷「6」的时候，机器人该做的不是想一句俏皮话 —— 是跟着刷「6」。

```
kaguya: 6
iroha: 6
小助手: 6        ← 插件自己接上的，模型完全没参与
```

表情包同理：连着两张一模一样的表情包/图片，它就把那张原样发回去。

```
kaguya: [一张表情包]
iroha: [同一张表情包]
小助手: [同一张表情包]        ← 也是插件自己发的（图片走 base64 出站）
```

这条链路**不经过 Agent**：没有 user message、没有 turn、不建会话，也就没有「等模型回话」
那几秒的延迟，更不会占用会话记忆。判定规则都在插件里：

- **只在群里**（私聊不谈复读），并且仍然受 `groupChat` / `allowGroups` 约束。
- **只跟没 @ 机器人的消息**：被 @ 的那条会走 Agent 去回答，再复读一遍等于同一句话回两遍。
  被 @ 的消息照样会**打断**「连着」——群里插了别的话，前后两条就不再是连续的。
  于是 `groupTrigger: all` 时每条都算被 @，复读自然不会触发（那种配置下它本来就在逐条回话）。
- **只有两种消息跟得动**：
  - **一条纯文字**：比较时只做 trim + 折叠空白，所以 `6` 和 `6 `、多打了几个空格算同一句；
    真正复读出去的是**后一条的原样正文**（复读机不改人家的字）。超过 `repeatMaxChars`
    （默认 100 字）的长段落不跟。
  - **单独一张表情包**：整条消息就是一张图（`image` / 商城表情 `mface`）或者一个系统表情
    （`face`，也就是 `[表情]`）。图片认「同一张」分两层：**字节完全相同**，或者**画面指纹
    足够近**（`repeatImageTolerance`，默认 0.08）—— 因为 QQ 会把同一张表情包**按发送者
    重新编码**，同一张「寿来」在群里出现过 94657 字节(progressive+Exif) / 131307 字节
    (baseline) / 79284 字节三种形态，画面 SSIM ≥ 0.985 却没有两份字节相同；只看字节的话
    表情包复读在真实群里几乎永远不会触发。指纹怎么算、怎么校准见下一小节。
    图 + 文字、一条里两张图、带引用的消息都不算候选（复读要的是「原样接上一张/一句」，
    把图和话拆开就不是那回事了）；`repeatMedia: false` 只保留文字复读。其余消息（语音、
    卡片、`@某人`、取不到字节的图）一律不跟，但**同样会打断链** —— 群里插了别的话，
    前后两条就不再是连续的。
- **默认要有两个人说**（`repeatDistinct`）：一个人自己连发两遍是手滑，不是复读。三个人一起刷时，
  第一个人说、第二个人接、第三句由它来接。`repeatCount: 3` 则是等第三个人接上才跟。
- **中间隔太久不算连着**（`repeatWindowMs`，默认 5 分钟，`0` = 不限）：早上有人说过的一句，晚上不该再被跟一遍。
- **跟一次就断链**：跟完这句/这张图链就清空，下一条相同的消息要**重新**攒够人数。否则群里一直刷
  同一个字时，它会一句不落地跟着刷成一台真·复读机。
- `repeatChance`（默认 1）是「每次都跟」之外的另一种玩法：调成 0.5 就成了偶尔跟一句的群友；
  这次没跟的话链还留着，下一条相同的消息会再掷一次。

发出去的是**原样的东西**：文字就是那条文字，图就是那张图——连「它是表情还是普通图片」都照
原消息，表情复读出去带的还是 QQ 的大表情标记（见[表情包那一节](#qq_send_image-工具显式动作可以发给别人)），
截图/照片仍是普通图片；都不带引用、不带 @、不加打字延迟（复读机的笑点就在「原样、立刻」）。
它挂在同一个会话的发送队列上，所以不会插到一轮正在分条发出的回复中间。

### 表情包那半边的账要算清

判「是不是同一张」需要先拿到字节，而字节得先下载下来 —— 这笔带宽**不额外花**：复读用的正是
群聊环境上下文那次落盘（见[像真实群友一样说话](#像真实群友一样说话)里的 `ambientMessages` /
`ambientMedia`；`mediaFor` 按消息对象共用同一次下载）。于是：

- 默认配置下，表情包复读的带宽成本是 **0**（环境上下文本来就要下这张图）；
- `ambientMedia: false` 或 `ambientMessages: 0` 时群里的图根本不会下载，表情包复读就自动
  退化成「只复读文字」—— 「不为闲聊花带宽」这个承诺不会被复读偷偷破坏；
- `imageSend: false` 时一律不发图（那是「不往 QQ 发图」的总开关），`repeatMedia: false` 则是
  只停掉复读里的图；
- 比 `imageMaxBytes` 还大的图不跟（跟了也发不出去），取不到字节的图也不跟。

**画面指纹是怎么算的**：只在真的要拿两条**字节不同**的图比一比时，插件才读一次刚落盘的那张图，
用纯 JS（零依赖）把它缩成 16×16 灰度再取 dHash（16×15 = 240 位）；两条消息的位差比例
≤ `repeatImageTolerance`（默认 0.08）就算同一张。指纹按内容哈希路径缓存（最多 64 张），
所以同一张图刷来刷去只解一次；绝大多数表情包消息（旁边没人接、链是空的）一次解码都不做。
几条实现上的取舍：

- **JPEG 只解 DC 系数**（它正好是 8×8 块的平均亮度，本身就是一张 1/8 缩略图），PNG 走
  `node:zlib`，GIF 手写 LZW 取第一帧；不认识的格式（WebP、CMYK 的四分量 JPEG）与解不动的
  （隔行 PNG）直接不给指纹 —— 这时退化成「只认字节完全相同」，宁可漏跟一次也不跟错一张图。
- **三条路都先降到 1/8 块平均再比**：否则同一张画面「一次以 JPEG 发、一次以 PNG 发」时平均
  窗口对不齐，实测能差 5%~26%，跨格式就认不出来了。
- **阈值是量出来的**：同一张重新编码差 0%~2%（跨格式 2%~4%），同一套画风只换了文字的表情
  差 16%~23%（实测「寿来」vs「萝莉来」= 23%），0.08 两边都有 2 倍以上余量。
- **透明像素按白底合成**（GIF 的透明索引、PNG 的 alpha），否则同一个透明背景的贴纸在 GIF 里
  是黑底、在 JPEG 里是白底，指纹根本对不上。
- 画面短边不到约 128 像素、或者整张几乎一个颜色的图不给指纹（1/8 缩略图撑不起 16×16 网格，
  纯色图则会让「任何两张纯色图都算同一张」）。
- 指纹解码走的是**群里的不可信字节**：所有尺寸、块数、扫描数、解压长度都有硬上限，任何畸形
  输入都只返回「没有指纹」这一个结果，绝不抛异常。

代价是「真要跟的时候」多一次本地读 + 一次纯 JS 解码（JPEG 只解 DC，几毫秒；大 PNG/GIF 也就
一百多毫秒，且算过就缓存）；`repeatImageTolerance: 0` 时连读盘都不做，回到「只认字节完全相同」。

> 复读的内容**全部来自不可信的群消息**，所以这条路径一步都不多做：文字原样发出，
> `[[图片: …]]` 这种标记在文字里只是字面文字，不会被当成发文件的指令（标记只解析模型写的
> 回复）；图片只可能来自 `.qq-media` 里刚落盘的那一张（内容哈希命名），不会去读工作目录里的
> 其它文件；系统表情只认纯数字 id，不把 OneBot 给的字段原样转发出去。

相关配置：`repeat` / `repeatMedia` / `repeatCount` / `repeatDistinct` / `repeatWindowMs` /
`repeatMaxChars` / `repeatChance` / `repeatImageTolerance`；`/reset` 会连同该群的复读链一起清掉（那是「刚才」的事，不属于哪一轮会话）。

## 偶尔主动说话（`proactive`）

复读是「跟着别人说」，这一条是反过来：**群里安静下来之后，它自己想一句冒个泡**。

```yaml
config:
  proactive: true        # 默认 false：它会主动给真人发消息，开不开由你决定
  proactiveChance: 0.35  # 每次「考虑」时真的开口的概率
  proactiveDailyMax: 4   # 每个群一天最多主动说几次
```

默认**关闭**。打开后，它也只在**群**里说话 —— 私聊对象是具体的人，被机器人无端戳一下
比在群里搭一句话冒犯得多，所以私聊**永远**不会被主动打扰（没有对应的开关，这是刻意的）。

**它说什么？** 不是模板，是让模型带着上下文自己想：插件往**这个群自己的那个会话**里
投一条提醒（「这个群已经安静了大约 N 分钟，你可以自己冒个泡」），模型看到的仍然是同一套
系统提示、同一份长期记忆、同一段[群聊环境上下文](#像真实群友一样说话) —— 于是它接得上的
是真在聊的话题，而不是一句「大家好啊」。回复走**同一条拟人通道**（拆短句 + 打字延迟），
和平时回话没有任何区别。

**什么时候会开口？** 定时器每 `proactiveCheckMs` 醒来一次，醒来的那一刻要同时满足：

| 条件 | 配置 | 为什么 |
|---|---|---|
| 在「清醒时段」内 | `proactiveFromHour` / `proactiveToHour` | 真人凌晨不会突然在群里冒泡 |
| 群里安静够久了 | `proactiveIdleMs` | 有人正在聊的时候插嘴最不像人 |
| 上一条**不是**它自己说的 | — | 它刚说完、没人接话时再开口就是**独白**，真人不会对着空群自说自话 |
| 这个群最近活跃过 | `proactiveFreshMs` | 三天没人说话的冷群突然冒一句最吓人 |
| 距上次主动说话够久 | `proactiveGapMs` | 同一个群别连着搭话 |
| 今天的额度没用完 | `proactiveDailyMax` | 一天最多几次（本地日界线） |
| 掷骰子中了 | `proactiveChance` | 让「开口的时刻」不可预测，而不是每到整点就说话 |

一次醒来最多只在**一个**群里开口（哪个群也是随机的）—— 同时在几个群冒泡比不说话更像机器。
另外它只对**已经聊过的群**生效：`conversations` 里没有的群（从没人 @ 过它、它也没回过话）
不会成为候选，重启之后也要等那个群再有人说话才会重新进入视线的范围。

**可以什么都不说。** 提醒里给了模型一个「我不说话」的出口：整条回复写 `SKIP`（后面顺手
带一句括号里的解释也行），插件就一个字都不发。这是**正常且常见**的选择 —— 不给出路时，
模型面对「没话找话」的场景会硬编一句，那正是最像机器人的地方。

这个出口是**整个会话**的，不限于主动搭话那一轮：提醒落在同一个会话的上下文里，模型很
容易在**回别人**的那一轮（尤其那一轮还引用了消息的时候）也照样写一个 `SKIP`。所以判据
对所有轮次都生效，否则群里收到的就是一句字面的 `SKIP` —— 那句话本来是「什么都不做」的
意思（见 `speaking-rules.js` 的 `proactiveSkip`）。

几条实现上的取舍：

- **掷中就消耗机会**：判成 `SKIP`、或者这一轮失败，`proactiveGapMs` 与当天额度照样扣掉。
  否则每次检查都会重新掷骰子，`SKIP` 会变成「再来一次」，开口频率直接失控。
- **出错不道歉**：主动搭话的 turn 失败时**不会**在群里回「我这边处理时出错了」——
  根本没人问过它，那句话只是噪音（平时回话失败时照旧会提示）。
- **状态在内存里**：`lastProactiveAt` / 当天计数随重启清零。重启后至少还要等
  `proactiveIdleMs` 才可能开口，所以正常重启不会让它多说话，但**别把 `proactiveIdleMs`
  设成 0 又反复重启**（那时每次重启都可能补一句）。
- **每次搭话都是一次模型调用**：这是「不是模板」的代价。把 `proactiveCheckMs` 调大、
  `proactiveChance` 调小，花的钱就少。

排查：日志里主动搭话会记一条 `... 已经安静 N 分钟，主动开个话头`，说出去的那句标着
`（主动）`，判成 `SKIP` 时记 `（判成 SKIP，不发送）`。`/reset` 会连同该群的主动说话
计时与计数一起清掉。

## 聊起来之后保持搭话（活跃对话）

上面那套 `proactive` 只在**冷场**（群里安静 45 分钟）之后才开口 —— 可真人聊起来的时候
不需要你每句都叫一遍名字，也不会在你说完十秒之后就彻底闭嘴。这一节是「正聊着」的那一半，
三件事共用一个**活跃对话窗口**：

```yaml
config:
  activeWindowMs: 60000    # 被 @ 到之后的 1 分钟里算「还跟你聊着」（多人搭话也用它量热度）
  activeFollow: true       # A：窗口里同一个人接着说的话也当作在跟它说（默认关）
  activeChimeIdleMs: 20000 # B：它回完之后你安静 20 秒，它可能再补一句（需要 proactive: true）
  activeGroupLines: 6      # C：最近窗口里大家说够 6 条话就进入「多人搭话」
  activeGroupSpeakers: 2   # C：而且至少要有 2 个不同的人说过话
  activeGroupBatchScale: 2 # C：搭话状态里攒批窗口 ×2 —— 多听几句再合成一轮回复
  activeTalkChance: 0.05   # A/C：够资格之后接话的起始概率（抽卡）
  activeTalkChanceStep: 0.1 # A/C：每多一条没抽中的消息，概率涨这么多
  activeTalkChanceMax: 0.8 # A/C：概率上限
```

**窗口怎么算**：被叫到（群里的 @ / 前缀，或私聊的一条消息）就开一个窗口，之后**同一个人**
每接一句就往后滑 `activeWindowMs`。窗口只靠**别人发来的消息**往后滑 —— 机器人自己说十句也
撑不住这个窗口。**默认只有 1 分钟**：@ 它一次买的是这一小段，不是「这一整天它都归你」；
想让它陪你聊久一点就把 `activeWindowMs` 调大。

**A：免 @ 接话（`activeFollow`，默认关）**

`groupTrigger: mention` 的意思是「只在被 @ 时说话」，这符合「不打扰群」的默认预期，代价是
聊起来之后你每句都得 @ 一下，很出戏。打开 `activeFollow` 之后，窗口内**那个人**接着说的话
不再需要 @。四条同时成立才算「够资格接话」：

- 说话的就是**正在跟它聊的那个人** —— 别人冒一句不会被它抢答（除非那句让群聊热到 C 的门槛）；
- 这句**没有 @ 别人**（`@某人`、`@全体` 都不算跟它说的）；
- 中间**没有别人说过话**（它记着群里最后一句接话时的进度序号）：有人插过话，你俩这段
  一对一就算断了，要重新叫它一次；
- 这次对话考虑过的免 @ 消息还没到 `activeMaxTurns`（默认 10），够数就要重新叫它。

够资格之后**还要抽一次卡**（见下面的「够资格之后还要抽一次卡」）—— 不是每句都回。

也就是说：**它放松的是「被叫到之后」的约定，不是把 `mention` 变成 `all`**。私聊不需要这条
（那边每条消息本来就都是跟它说的），所以 `activeFollow` 只在群聊生效。

**B：自己补一句（`activeChime*`）**

人常有「啊对了」：回完一句、对方沉默了一会儿，再追一条。前提是 `proactive: true`（「允许它
主动发消息」的唯一总开关）。满足之后，它在**正常回完一轮**、对方安静超过 `activeChimeIdleMs`
（默认 20 秒，按 `delayJitter` 抖动）、中间没有别人插话、这条消息之后还没补过
（`activeChimeMax`，默认 1 句）、当天没超量（`activeChimeDailyMax`，默认 12 句）时，才掷一次
`proactiveChance` 决定补不补。补的那句问的是「你已经回过他了，还有想说的吗」，同样可以回
`SKIP` 一个字都不发。

**C：多人搭话（`activeGroup*`）**

一个人 @ 一次只买到 1 分钟，但几个人**自己聊起来**的时候，它不该还在旁边等 @。所以除了
一对一窗口，它还看着群里的「热度」：最近 `activeWindowMs`（默认 1 分钟）里，**别人**说的话
累计够 `activeGroupLines`（默认 6）条、并且来自 `activeGroupSpeakers`（默认 2）个不同的
人，就进入**搭话状态** —— 那之后群里**谁**接话都算数（但仍然要过下面那次抽卡），直到这个
窗口里凑不齐条数或人数（大家一停，它自己就退出，不需要谁通知它）。

搭话状态里它的**倾听时间变长**：攒批窗口与整批等待上限一起乘 `activeGroupBatchScale`
（默认 2），也就是「多听几句再合成一轮回复」，而不是每两秒截一句就回。两个条件一起卡住
两类误判：一个人自己刷屏凑不出「几个人」，两个人半天说一句也凑不出「聊起来了」。
`activeGroupLines: 0` 可以整块关掉多人搭话，只留一对一的免 @ 接话。

别人插一句因此不再是「你们聊完了」的信号：那句话本身就会让热度往门槛上走，够热就整体升级
成多人搭话（这也是它不消耗 `activeMaxTurns` 的原因 —— 那个上限是防一个人揪着它刷屏的）。

**够资格之后还要抽一次卡（`activeTalkChance*`）**

A 与 C 都只决定「够不够资格」，够资格不等于就接 —— 每条够资格的消息还要掷一次**会自己涨**
的概率，像抽卡那样：

- 起始概率是 `activeTalkChance`（默认 5%）；
- 每多一条**没抽中**的消息，下一次的概率就加上 `activeTalkChanceStep`（默认 +10%），
  直到 `activeTalkChanceMax` 封顶（默认 80%）—— 也就是「连着几句没接上，就越可能接一句」；
- 抽中、或者被明确 @ 到（那是不用抽的直接回复）之后，累计归零，重新从 5% 攒；
- 这段对话凉了（一对一窗口过期、群也不再算聊热）之后累计同样归零 —— 上一场聊天攒下来的
  「保底」不会在下一场开头突然炸出来。

没抽中的那条**什么都不发**（但它照常进转录、环境上下文与群聊热度），所以群里看到的是
「它偶尔接一句」，而不是「聊热了它就每条都回」。A 路里没抽中的消息仍然算「人还在跟它说话」：
一对一窗口照滑、`activeMaxTurns` 照扣 —— 否则窗口会在概率攒够之前先过期，那条路就名存实亡了。

> 这套曲线让「搭话频率」变成一个可调的数：想让它更爱接就调大 `activeTalkChance` 或
> `activeTalkChanceStep`，想让它在热群里彻底闭嘴就把 `activeTalkChance` 与 `Step` 都设成
> `0`（那就永远不会接）。被 @ 到的话永远照常回，抽卡只影响「免 @ 搭话」这一层。

几条要点：

- **不会连珠炮**：对方每说一句之后最多补 `activeChimeMax` 句；它自己补的那一句**不会**再
  触发下一次补（否则就成了对着空气自言自语）。
- **对方又说话就作废**：挂着的「补一句」会被新消息取消 —— 那条消息自己会走正常回复，
  不需要它再补。
- **接话不是指令**：窗口里免 @ 接上的那句只当闲聊交给模型，`/reset` 这类旁路仍然
  要求明确叫它（@ 或前缀）—— 否则窗口里随便一句「reset」就绕开模型把会话重置了。
- **私聊也补，但冷场不主动**：私聊里窗口照样滑，所以它会在你回完、安静一会儿之后追一句；
  而「主动找人聊天」（冷场开口）仍然只在群里发生。这就是[偶尔主动说话](#偶尔主动说话proactive)
  里那句「私聊永远不主动打扰」的边界 —— **聊着的时候可以补，没人理的时候不会去戳你**。
- **`/reset` 把「还聊着」也一起忘掉**：一对一窗口、多人搭话的热度、抽卡攒下的概率、挂着的
  补一句都作废（新开的那一轮不带这些）。
- 日志里补的那句标 `（主动）`，并且前面会有一条 `... 对话还热着（对方安静了约 N 秒），主动补一句`。

> 为什么一对一那么保守：群聊是公开的，别人一插话，你接着说的一句很可能是冲着他去的。
> 宁可少接一句，也不要抢话 —— 想继续聊，重新 @ 它一下；而如果大家本来就在聊，走的是上面
> C 的多人搭话，不需要谁来叫它。


### 私聊补一句（L2，默认开）

群聊的「补一句」跟着 `proactive`（那是在群里主动开口的总开关）；**私聊的补一句不搭那趟车** ——
它是对着一个具体的人「刚聊完、再看有没有想补充的」，语义不同，所以有自己的开关与额度：

- 只私聊；只在你**正常回完一轮之后**挂一次（命令、出错、SKIP、空消息之后的轮次不补）；
- 对方安静 `privateAfterthoughtIdleMs`（默认 15 秒，会抖动）之后才考虑；
- 对方在这期间**又说话了** → 不补（那句自己会走正常回复）；
- 一次用户消息最多补一句，不连锁；当天到 `privateAfterthoughtDailyMax`（默认 10）就停；
- 概率 `privateAfterthoughtChance`（默认 0.3）；判成 `SKIP` 就一个字都不发。

它仍然属于「主动给真人发消息」，所以上面每一条都是一道闸；`privateAfterthought: false`
一键关掉。

## 没有正文的消息（`blankReply`）

「@ 它一下什么也不说」和「私聊发一个空格」都是**明确叫了它、却没写事**。默认
（`blankReply: true`）这两类消息不再被丢掉，而是照常走一轮：插件把正文位置换成一句说明，
模型看着这段聊天的上下文（群里还有「群里最近的消息」，更早的用 `qq_transcript` 查）
自己决定回什么 —— 常见的就是回个「？」、发一张 `[[图片: …]]` 表情，或者顺着上一句接一句。

```
QQ: @机器人          →  模型看到的正文： （@了你一下，没有说别的）
QQ: （私聊）一个空格  →  模型看到的正文： （对方发来一条空消息，什么都没写）
```

三种措辞分开写，因为对模型的含义不同：群里被 @ 是**点名**，群里没 @（`groupTrigger: all`，
或者活跃对话窗口里接上的一句）只是这句话恰好是空的，私聊则没有 @ 这回事。正文里那对括号
是插件加的说明，不是谁发的字 —— 提示词里也会讲清楚，免得它回一句「你发了什么」。

几条边界：

- **空 @ 不是指令**：`/reset` 这类旁路照样只认**明确叫了它且有正文**的消息，
  空 @ 永远只走模型。
- **空 @ 不打断攒批**：有人 @ 一句「在吗」、紧接着又空 @ 一下，两句会攒成同一轮
  （正文分别是两行），而不是一前一后回两次。
- **活跃对话窗口里接上的空消息不算接话**：那只是「他说了句话，正好没内容」，不是点名，
  接上去就成了抢答（见[聊起来之后保持搭话](#聊起来之后保持搭话活跃对话)）。
- **前缀模式下 `"/"` 后面没内容不算**：那是没内容可切，不是「空消息」，别硬凑一句话回。
- **`blankReply: false`**：回到旧行为，空消息一律静默丢弃（群里被人反复空 @ 时可以一键关掉）。
- **想让它只发表情、一个字都不说**：靠回复正文里的 `[[图片: …]]` 标记，
  见[只发表情、一个字都不说](#只发表情一个字都不说)。


## 图片与表情包：它能真的「看」图

QQ 那边发来的图，在 OneBot 里只是一个**会过期的下载链接**：NapCat 上报的 `image` 段长这样

```json
{"type":"image","data":{
  "summary":"[动画表情]",
  "file":"695E1A06A7D44ECF81DE064CCF51674E.jpg",
  "sub_type":1,
  "url":"https://multimedia.nt.qq.com.cn/download?appid=1407&fileid=…&rkey=…",
  "file_size":"11279"}}
```

而模型要「看见」图只能靠 `read_image` 读**本地文件**。所以插件在消息入队前多了一步：
取字节 → 按魔数认出真正的格式 → 以内容哈希命名落进 `mediaDir` → 把路径写进正文。

```
QQ: [一张表情包] 你看这个
        ↓
Agent 收到的正文： [图片(动画表情): .qq-media/6ab290670daf12d2688c6364efca45d5.jpg] 你看这个
        ↓
Agent 调 read_image(".qq-media/6ab290670daf12d2688c6364efca45d5.jpg") —— 真的看到了
```

几个要点：

- **为什么必须马上下载**：那个 `rkey` 是有时效的签名，过一会儿同一个 URL 就 403 了。
  发给机器人的那条在消息入队时下载（同一会话串行，所以顺序是「先落盘、再交给模型」，
  被引用的那条也一样）；群里闲聊的那条则在后台下载，不挡任何人的消息。
  抓不动时还有一层兜底：把 `file` 段丢回 OneBot 的 **`get_image`**，让它把图（可能以
  base64 形式）给我们。
- **`mediaDir` 下的文件**按内容哈希命名、扩展名来自**字节里的魔数**（腾讯的链接根本不带
  扩展名）。同一张表情包被反复发只会存一份；超过 `mediaCacheFiles` 就按最近使用时间淘汰
  最旧的；单个文件超过 `mediaMaxBytes` 连请求都不发。`mediaDir` 必须在 `cwd` 里 ——
  写到工作区外面 Agent 反而读不到，所以这种情况下插件会整体停用下载并打一条 warn。
- **正文里可能出现三种形态**，含义不同：
  - `[图片(动画表情): .qq-media/…jpg]` —— 已落盘，路径相对 `cwd`，可以直接 `read_image`；
  - `[图片(动画表情) 没能取到文件: HTTP 403]` —— 抓失败了（rkey 过期、CDN 抽风），别去读
    一个不存在的路径，可以直说图挂了；
  - `[图片(动画表情)]` —— 没有本地路径的纯占位符：下载整体关掉（`mediaDownload: false`）、
    闲聊里的图还没在后台落完（`ambientMedia`）、或者这张连字节都没认出来时会是这样。
- **群聊环境上下文里的图也下载**（`ambientMessages` 那一段，`ambientMedia: true` 默认）。
  「别人刚才发的那张表情包」是最常被接着问的东西，所以闲聊里的图也会落盘，只是下载在
  后台进行：等提示词渲染时那一行已经变成 `kaguya: [图片(动画表情): .qq-media/…jpg]`。
  同一张表情包按内容哈希去重，磁盘只存一份；但每次发出来仍会重新下载一遍字节 ——
  腾讯的下载链接每次都带新的 `rkey`，没法只靠 URL 判断「这张我见过」。
  不想为闲聊花带宽就设 `ambientMedia: false`，那时上下文里只有 `kaguya: [图片(动画表情)]`。

### 被引用的那条消息也能看见

QQ 的「引用回复」在 OneBot 里只有一个 `reply` 段，里面**只有被引用消息的 id** ——
没有正文、没有图。所以「引用一张表情包再 @ 它问这是啥」这种最常见的用法，光看入站事件
是什么也看不到的。插件因此在入队时多取一趟：

```
QQ: [引用 kaguya 的表情包] @bot 这啥
      ↓  reply 段只有一个 message_id → get_msg
Agent 收到的正文：（引用 kaguya: [图片(动画表情): .qq-media/6ab290670daf12d2688c6364efca45d5.jpg]）
              这啥
      ↓
Agent 调 read_image(".qq-media/6ab290670daf12d2688c6364efca45d5.jpg")
```

- 引用的**正文**也会带进来（最多 200 字，够当锚点又不挤上下文）；引用段本身那个
  `[回复]` 占位符会被替换掉，不会出现「一半有内容、一半是噪音」的正文。
- `get_msg` 拿不到时（实现不支持、消息已撤回、网络抖动）只记一条 warn，正文里保留
  `[回复]`，消息照常投递 —— 引用只是锦上添花，不该拖垮聊天。
- 只取**一层**：被引用的那条自己再引用别的东西，不会跟着递归下去。
- 关掉：`quoteMedia: false`（回到「引用段就是一句 `[回复]`」，一次 `get_msg` 都不发）。
- 合并转发（`forward`）不吃这一套，仍是 `[合并转发]`。

### 商城表情 / 系统表情 / CQ 码，各是什么下场

| QQ 里的东西 | OneBot 上报成 | 插件怎么处理 |
|---|---|---|
| 普通图片、图片表情包（含动图） | `image`（带 `url`） | 下载 + 落盘，模型能看 |
| 商城表情 / 收藏表情包 | **NapCat 上报成 `image`**（带腾讯 CDN 的 `url` 和表情名 `summary`） | 同上；表情名会进占位符的括号里 |
| 商城表情（其它实现，如 Lagrange / go-cqhttp） | `mface`：只有 `emoji_id` + `summary`，没有可下载的 URL | 只渲染 `[表情包(表情名)]`，不下图 |
| QQ 系统小表情 | `face`：只有数字 id | 仍是 `[表情]` —— 这个段里没有图、也没有语义表，要「读懂」得配一张 id→含义的表，属于另一件事 |
| 引用回复 | `reply`：只有被引用消息的 `message_id` | 多调一次 `get_msg` 把被引用的那条取回来：正文与图都进正文，见[被引用的那条消息也能看见](#被引用的那条消息也能看见) |

> 上面这张表是拿真实 NapCat（`mlikiowa/napcat-docker`）的事件实测出来的，不是照着协议
> 猜的：QQ 的 marketFaceElement 在 NapCat 里会被直接转成 `image` 段并附上
> `https://gxh.vip.qq.com/…` 之外的 `multimedia.nt.qq.com.cn` 下载链接。

### 前提：模型得支持读图，工具得放开

- `read_image` 只有当前模型声明了 **image 输入**才可用（部署默认的 `deepseek-flash`
  声明了 `["text","image"]`）。换成纯文本模型时 `read_image` 会直接报
  `model "…" does not declare image input` —— 那时落盘仍在发生，只是模型读不到，
  它在正文里看到的仍是一句带路径的占位符。
- 部署的附件服务只接受 **PNG / JPEG / WebP / GIF**，所以插件只认这四种（认不出就不落盘）。
- `qq` 预设里有 `tool-fs`（含 `read_image`），`allowTools` 里也放开了它。**如果白名单把
  `read_image` 挡掉**，插件不会再在提示词里推荐它（免得模型去调一个看不见的工具），
  图也就只能停在占位符上。
- 关掉整个功能：`mediaDownload: false`。此时一条网络请求都不会发，正文里只有朴素占位符。

排查用 `/reset` 一样清不掉的东西就是缓存本身（它按内容去重，与哪个会话、哪一轮都无关）；想手动清：

```bash
rm -rf ~/Projects/qqbot/.qq-media
journalctl --user -u qqbot -f | grep 'qq-bridge: media:'   # 每张图的落盘/失败都会记一行
```

## 它也能发表情包

上面那一大节是「QQ 的图 → 本地文件」，让模型能**看**图；这一节是反方向：让模型能**发**图。

```
模型想接个梗 / 想回一张图
      ↓  回复正文里写一行「表情包标记」：[[图片: .qq-stickers/笑死.gif]]
插件读字节 → 认格式 → 校验大小（只认 PNG/JPEG/WebP/GIF，默认 ≤ 8MB）
      ↓  send_group_msg / send_private_msg 的 image 段：
         {"type":"image","data":{"file":"base64://…","sub_type":1}}
NapCat 解码 → 上传 → 图出现在 QQ 里（`sub_type: 1` = 按「大表情」渲染，见下）
```

### 只发表情、一个字都不说

这是最要紧的一条：**整条回复只写一行 `[[图片: 路径]]`，就只会发出那一张图，一条文字都没有。**

```
模型的回复正文：
[[图片: .qq-stickers/笑死.gif]]
        ↓
群里只多了一张表情包 —— 没有「给你发张表情包」这种话
```

为什么不用工具做这件事：工具调用发生在整轮文字**之前**，而且「不说话」在纯文本回复里
根本表达不出来（模型总得写点什么）。把表情写成正文里的一处标记，位置就跟着正文走：

```
模型的回复正文：                    群里依次看到：
今天真累啊                          今天真累啊
[[图片: .qq-stickers/摸摸头.gif]]   [一张摸头图]
早点睡                              早点睡
```

标记里的路径也可以**只写文件名**（`[[图片: 笑死]]`、`[[图片: 笑死.png]]`）：
在 `.qq-stickers/` 里找得到就用那一张（带不带扩展名都行），找不到才按工作目录的相对路径算。
关键字给几种写法（`图片` / `图片表情` / `表情包` / `表情` / `贴图` / `sticker` / `image` /
`img`），全角冒号也认。**认不出来的方括号一律当普通文字发出去** —— 宁可群里露出一行 `[[音频: x]]`，
也不要静默吞掉模型说的话。**标记只认 `.qq-stickers/` 里的文件**：`.qq-media/<哈希>` 这类缓存路径、工作目录里的其它文件
都会被直接拒绝，并回一句「（那张表情我这儿没有，发不出去）」+ 记一条 warn。失败原因还会
写回下一轮提示词 —— 否则模型会照着自己编的路径再编一个（真实事故：连编两轮，用户连收两遍
「没发出去」）。只发表情的那条回复要是静默失败，看起来就是「机器人没理人」。

### `qq_send_image` 工具（显式动作，可以发给别人）

标记只能作用于「正在回的这条会话」；要给**别的**群/好友发图，或者就是要一个明确的
「把这张图发过去」，用 `qq_send_image` 工具。它接受同样的来源，另外还接受 http(s)
图片链接（插件先在**宿主机**把它下下来，顺便校验格式与大小，而不是让容器里的 NapCat
去够那个链接）。它是立刻发出去的，不跟在正文的行序里。

要点：

- **按「大表情」发，而不是普通图片**：从 `.qq-stickers/` 发出去的表情，`image` 段带
  `sub_type: 1`（NapCat 会原样写进 QQ 的 `picSubType`；真人从表情面板发收藏表情时那里
  就是非 0 的）。不带这个标记，QQ 只当它是一张照片：带边框、按原图像素铺开，群里一眼
  就看得出不是人发的。反过来，`.qq-media/<哈希>` 里的截图、URL、工作目录里的照片都
  **不**带这个标记 —— 被 QQ 当成表情裁成小图更糟。**复读是照原消息发**：原消息是表情
  （`sub_type` 非 0 的收藏表情 / 带 `emoji_id` 的商城表情）就带标记，原来是截图/照片就
  仍是普通图片，判据见 `isStickerSegment`。
- **表情包放哪儿**：`stickerDir`（默认 `.qq-stickers/`，插件启动时会自动建好）。
  往里丢几张图就能用 —— 文件名会列进「QQ 渠道」提示，所以**名字起得有意义**最划算
  （`笑死.gif`、`摸摸头.png`）；名字看不出来的，模型可以先 `read_image` 看一眼再挑。
  目录里超过 40 张时只列前 40 个（按文件名字典序），其余靠它自己 `glob`。
- **别人发的图想发回去，先存一次**：入站那张在 `.qq-media/…`（LRU 缓存，迟早被淘汰），
  标记不能直接用它。用 `qq_save_sticker` 存进 `.qq-stickers/`（顺手起个名字、写一句含义），
  下一轮就能挑它 —— 这也是「这张图以后还能再用」的唯一可靠办法。
  `qq_send_image` 工具仍然可以发 `.qq-media` 里的图（那是显式动作，不是「发表情」，
  所以按普通图片发；只有落在收藏目录里的路径才带「大表情」标记）。
- **权限边界没变**：本地路径只允许 `cwd` 里的文件，而且必须真的是 PNG/JPEG/WebP/GIF
  （按魔数判断，`.txt` 改名成 `.png` 也蒙不过去）—— QQ 那头是不可信输入，没理由为了
  发张图把工作区捅开。标记还**跟着 `allowTools` 走**：白名单里没有 `qq_send_image`
  时，回复里也不能用标记发图（那时它就是一行普通文字）。
- **提示词里已经写了这件事**：模型知道标记怎么写、知道「整条只写这一行就是只发表情」、
  也知道表情包目录里有哪几张、还知道「一次最多一张、别每句都配一张」。想让它更爱发或
  更克制，用 `persona` / `instructions` 补两句就行 —— 比「多发表情」这种态度更有效的是
  写清**什么时候**发：「表达无语 / 委屈 / 破防时先用表情，别用文字描述情绪」。
- **关掉**：`imageSend: false` 一次关掉标记与工具（工具调用会明确报错
  `sending images is disabled`，提示词里也不再提标记）；`imageMaxBytes` 调小可以进一步
  限制它能发多大。

### `qq_save_sticker` 工具（把别人发的表情留下来）

群里最常见的一句话是「存一下这个表情」。但 QQ 会话是按「不可信输入」配的：**没有
write / edit、也没有 bash**，所以模型自己没有任何办法把那张图留下来。不给它出口时它会
假装做到了 —— 实测它 `read_image` 看完、`glob .qq-stickers/**` 发现是空的，只能把含义
追加进 `COGNITION.md`，key 写成 `.qq-media/<内容哈希>` 这个**会被淘汰的缓存路径**，
然后回一句「存好了」。那张图一被 LRU 淘汰，这条记忆就指向一个不存在的文件 —— 现在这种路径会被
直接拒发（「（那张表情我这儿没有，发不出去）」），不会再默默失败。

`qq_save_sticker` 就是为这一句话开的窄通道：

```
[[图片: .qq-media/ab12….gif]]   模型在正文里看到的路径
      ↓  qq_save_sticker(source: ".qq-media/ab12….gif", name: "委屈")
魔数判格式 + 大小上限 + 必须在 cwd 内  →  名字清洗成单层文件名  →  同名不覆盖
      ↓
.qq-stickers/委屈.gif           下一轮提示词里就列出来了，以后随手能挑
```

边界（全部在 `index.js` 的 `saveSticker` 里，工具只负责参数与报错）：

- **只写 `stickerDir` 之内**，文件名由纯函数 `stickerFileName` 洗成单层名字：`../../etc/passwd`
  这类只会剩最后一段，控制字符与 `:*?"<>|` 被去掉，开头的点也去掉（隐藏文件列不出来，
  等于存了看不见）。
- **扩展名以真实格式为准**（按魔数嗅，不看模型写的那个）：否则会出现 `笑死.png` 里装着
  GIF 字节这种「发得出去、但看名字以为是别的格式」的坑。名字长度封顶 60 字符 ——
  它要进每轮提示词，太长的名字是纯 token 开销。
- **同名不覆盖**：覆盖等于群里任何一个人一句「存一下」就能把现有表情换掉。想换就先删掉
  旧的那张（或改个名字）。
- **张数上限 `stickerMaxFiles`**（默认 60，`0` = 不限制）：QQ 那头是不可信输入，群里谁都
  能让它一直存，磁盘不该被这么撑大。
- **不可用就不注册**：`stickerDir` 没配 / 配到 `cwd` 外、`imageSend: false`、或者
  `allowTools` 里没有 `qq_save_sticker` 时，这个工具**根本不出现**（与 `qq_transcript` /
  `qq_memory` 同一个规矩：不留「一调就报错」的壳），提示词里也不会提它。

顺带一句：如果你更愿意自己管这个目录，就把图直接丢进 `.qq-stickers/`、名字起成它的意思 ——
**文件名本身就是最便宜的那张「含义表」**，它每轮都在提示词里，而且不花一个 token 去查。
`COGNITION.md` 适合记「这张图是什么梗」（给看懂用），不适合当「挑一张发」的目录，
而且里面的 key 千万不要用 `.qq-media/<哈希>` 这种会过期的路径。

### 为什么是 base64，而不是把路径丢给 NapCat

现实是这样的：NapCat 跑在**容器**里、插件跑在**宿主机**上，容器的文件系统里没有
`.qq-media/xxxx.jpg`。给 `upload_*_file` 传本地路径实测会回 `识别URL失败`（它的
`enableLocalFile2Url` 默认还是关的），image 段里的本地路径同理。

所以这里用 OneBot image 段的 **`base64://`**：字节直接跟在 `file` 字段里发过去，
NapCat 自己解码落进它的临时目录（实测：同样一段 base64 喂给 NapCat 的 `download_file`，
容器里落出来的文件与宿主机的图 md5 完全一致），之后的链路与手动发图一模一样。
好处是不依赖任何「容器能不能连到宿主机」的假设 —— 另一种常见做法（把文件放在本机、
给 NapCat 一个 URL 让它自己来拉）必须绑在 docker 网桥上，这里不需要；代价是体积膨胀
约 4/3，所以有 `imageMaxBytes` 上限。

NapCat 的 WebSocket 服务端 `maxPayload` 实测是 **50MB**，默认 8MB 离它还很远。
真发超大图时唯一的代价是慢：`timeout.uploadSpeedKBps` 默认 256 KB/s，八兆的图要等
半分钟左右，所以默认值刻意压在「表情包 / 截图」的量级。

排查：

```bash
journalctl --user -u qqbot -f | grep 'qq-bridge: →'   # 每张发出去的图都记一行（目标、格式、字节数、来源）
ls -la ~/Projects/qqbot/.qq-stickers       # 表情包目录：丢几张图进去就能用
```

## 感知与互动（链接 / 视频 / 语音 / 戳一戳）

除文字与图片之外，消息里的其它东西现在都有确定的下场（`modalities.js` 把每一段变成
`Observation` 再渲染成占位符）。默认值全部偏保守 —— 这些输入都来自 QQ，是不可信输入。

| 消息里是什么 | 它看到什么 | 默认 |
|---|---|---|
| 图片 / 商城表情 | 下载到本地，正文给 `[图片: .qq-media/…]`，模型可以 `read_image` | 开 |
| 系统表情 `face` | `[表情: 名称]`（有名字时），没有就 `[表情]` | 开 |
| 语音 | `[语音 3 秒]` —— **只占位**：不下载、不转写、不起任何外部进程 | 开 |
| 视频 | `[视频 12 秒 · 封面: .qq-media/…]`：只下封面（`videoCover`），整段不下载（`videoMaxBytes: 0`） | 开 |
| 文件 | `[文件 report.pdf（1.2 MB）]`，不自动下载 | 开 |
| 合并转发 | `[合并转发 8 条]`（占位，不展开） | 占位 |
| 卡片消息（`json` / `xml`） | 解析出标题 / 摘要 / 域名 / 链接，渲染成 `[链接: 【标题】 — example.com https://…]`；解析失败退回 `[卡片消息]` | 开 |
| 正文里的裸 URL | 可选地抓一次**标题**（`linkPreview`） | **关** |
| 戳一戳 | 通知事件，按 `pokeMode` 回戳或走一轮模型 | 开 |

### 为什么链接预览默认关

卡片消息（`json` / `xml`）自带标题与链接，**不联网**就能解析 —— 群友分享文章时已经够用。
而「正文里一个裸 URL 就去访问它」等于：替群里任何人访问任意地址、把部署机器的出口 IP
暴露给发链接的人，还留下一次可被用来探测内网的请求。要开就显式开，并且它带着这些边界：

- 只认 `http(s)`；拒绝 `localhost` / `*.local` / `*.internal` / 单标签主机；
- 拒绝私有与保留网段（`10/8`、`172.16/12`、`192.168/16`、`127/8`、`169.254/16`、`100.64/10`、
  `224/4` 等），以及 `::1`、`fc00::/7`、`fe80::/10`、`::ffff:<私有 v4>`；
- 拒绝十进制 / 十六进制 / 八进制写法的 IPv4（`http://2130706433/` 这类）；
- **每一跳重定向都重新校验**（重定向到内网是最常见的绕过方式），最多 3 跳；
- 超时 `linkPreviewTimeoutMs`、最多读 `linkPreviewMaxBytes`、只收 `text/html` / `text/plain`；
- 一条消息最多抓 2 个链接；抓到的标题作为**数据**渲染，不是指令。
- 自建 wiki 之类确实在内网的，用 `linkAllowPrivateHosts: true` 显式放开（scheme 与重定向
  校验不会因此放松）。

### 戳一戳（`pokeMode`）

以前 `handleEvent` 第一行就把非 `message` 的事件全丢了，所以「有人戳了它一下」它完全收不到。
现在只认**戳机器人自己**的（戳别人一律不记：群里互相戳跟它无关）：

- `pokeMode: random`（默认）—— 按 `pokeReplyChance`（0.7）决定**回戳**还是**走一轮模型**；
- `pokeMode: poke` —— 总是回戳（最快、最像群友）；`text` —— 总走一轮模型（正文是「X 戳了
  你一下」，允许 SKIP）；`ignore` —— 不回；
- 每个会话 `pokeCooldownMs`（30 秒）冷却 + `pokeDailyMax`（20 次）每日上限 —— **防回戳
  死循环**：两个机器人互相戳起来时，冷却那条是唯一真正管用的闸；对方回戳不再触发连锁。
- 回戳只打给**戳它的人**（`target_id` 来自 QQ，是不可信输入，但不会拿去戳第三人）。
- 走模型的那一轮 `intent = poke`，不攒批、不引用、不消耗活跃对话轮数，但会更新「最后活动
  时间」—— 有人在跟它互动，群就不算安静。
- 它自己也能戳人：`qq_poke` 工具（群里必须显式指定戳谁，不做「最近跟我说话的人」这种推断）。

## 长期记忆：聊天记录 → 摘要 → 认知

默认开着。三件事：**每一句话都落盘**、**定时把它总结成记忆**、**聊天时随时能查**。

```
QQ 消息 ─▶ 转录(.qq-memory/…/log/YYYY-MM-DD.jsonl)         插件写，不经过模型
                 │
                 │  每天 digestAtHour（默认 04:00）醒一次：这个会话今天攒够了吗？
                 ▼
            独立「摘要会话」（qq_memory + qq_transcript + skill）
                 │  按 message-digest skill 读转录、写记忆
                 ▼
  conversations/<slug>/MEMORY.md   这个群的记忆           ┐
  COGNITION.md                     公共认知：语言梗 / 黑话  ├─ 摘要成 INDEX.md 的一行
  STICKERS.md                      表情包目录：名字 + 含义  ┘  每次提示词都带上
  INDEX.md                         短索引
```

**为什么是「摘要」而不是「把聊天记录塞回上下文」**：一个群一天的记录就能撑爆窗口，
而模型真正需要的是「kaguya是群主、周六打本、他不喜欢被叫大佬」这种**结论**。
转录是原料、记忆是成品 —— 成品每次进提示词，原料只在摘要与追问时才被翻。

### 记什么、记在哪

`memoryDir`（默认 `.qq-memory/`，**必须落在 `cwd` 内**，否则整个功能记一条 warn 并停用）：

| 路径 | 谁写 | 是什么 |
|---|---|---|
| `conversations/<slug>/log/YYYY-MM-DD.jsonl` | 插件 | 原始转录：每条**别人的**消息一行（含没 @ 机器人的群聊） |
| `conversations/<slug>/MEMORY.md` | 摘要 Agent | 这个会话的长期记忆（人、约定、偏好、在追的东西） |
| `COGNITION.md` | 摘要 Agent / 聊天中的模型 | 跨会话的公共认知：**只有语言**（梗、黑话、缩写、谐音；键是文字写法含变体） |
| `STICKERS.md` | `qq_save_sticker` / 摘要 Agent | 表情包目录：名字、画面、含义、场景、**收藏后的文件路径** |
| `INDEX.md` | 摘要 Agent | 「去哪里找什么」的短索引，每次提示词都注入 |
| `digest.json` | 插件 | 摘要进度（上次摘要时间 + **本地日期**），重启后据此补课、并保证一天至多摘要一次 |

`<slug>` 是会话 key 去掉冒号：`group:100000001` → `group-100000001`。

落到转录里的消息要**先过一遍准入规则**（私聊开关、群/私聊白名单）—— 记忆不会成为绕过
白名单的后门。机器人自己发出去的话不进转录：那是它说的话，不是群里的历史（本机 NapCat 的
`reportSelfMessage` 关着，这些消息其实也不会作为事件回来）。

### 定时摘要怎么跑

- **每天在 `digestAtHour`（默认凌晨 4:00，本地时间）醒一次**，醒来先跑摘要、再把下一次
  排到明天的同一个整点。挑凌晨是因为那时群里没人说话；每天一次也就意味着一个会话
  **一天至多摘要一次** —— 这条判据是「`digest.json` 里记的日期」（本地日界线），
  所以白天重启、重复启动都不会在同一天把同一个会话摘要两遍。
- 醒来后逐会话问两个问题：**今天摘要过吗**（日期判据）、**今天攒够 `digestMinLines`
  条新消息了吗**。攒不够就留到明天 —— 消息不会丢（计数一直累加），只是不为两三句话
  白跑一次模型调用。
- **错过就补课**（`digestCatchUp`）：如果摘要点那一刻进程正好在重启，或者这个会话是
  重启之后才有人说话的，那么它**一开口就补一次**，而不是等到明天。补课每次启动只跑
  一轮，不是每条消息一轮。
- 摘要在**独立会话**里跑（session id 由 `bridge:digest` 确定性派生）：它没有人格、
  不挂在任何 QQ 会话上、输出**不会**发到 QQ。它拿到的正文就是这段时间的转录，
  并被告知要处理哪个会话。
- 一次摘要最多喂 `digestMaxChars` 个字符（超出按**最近优先**截断，并在提示里说明
  前面还有更早的记录），单次有 `digestTimeoutMs` 硬超时：卡住的摘要 Agent 会被销毁，
  下次重新开一个，不让一个死掉的 turn 把摘要永久堵住。
- 摘要会话本身也有上下文窗口，但它**不是**记忆的载体：记忆在磁盘上、由 `qq_memory`
  读进来 —— 所以就算那个会话被压缩、被重启，记忆也不会丢。

### 聊天时怎么用

- **`qq_transcript`**：`list`（哪些会话有记录）／`read`（按会话读，可给日期范围）／
  `search`（按关键词找原话）。提示词里只放最近 `ambientMessages` 条，更早的靠它翻。
- **`qq_memory`**：`read`／`append`／`write`／`search`／`list`，外加两个**逐条**动作：
  `upsert`（按名字新增或替换一条认知 / 表情包条目，只给字段、格式与分节由代码生成）与
  `remove`。`write` 仍是整份覆盖，但有护栏：**条目数掉到 90% 以下直接被拒**（除非
  `force: true`）；每次写入前还会把旧版本存进 `<memory>/.history/`（每个文件留最近 20 份）。
  **写被限制在 `memoryDir` 之内**（`../`、绝对路径都直接报错），并有单文件字节上限 ——
  QQ 会话因此始终拿不到 `write` / `edit` / `bash`，能力面没有被记忆功能放大。
- **`INDEX.md` + 本会话的 `MEMORY.md` 每次提示词都注入**（有 15 秒缓存，上限 4KB）：
  模型一开口就「知道自己记得什么」，而不是先撞一次「不知道」再去查。

两个工具都在**宿主平面**注册，所以 Web UI 里的主会话也能直接用来翻记录 / 读记忆。

### 五个 skill（`.dsh/skills/`）

| skill | 什么时候加载 | 写哪 |
|---|---|---|
| `message-digest` | 定时摘要的那一轮；或有人在群里问「以前说过什么」需要系统整理时 | `MEMORY.md` / `INDEX.md`，并按分诊规则转给下面两个 |
| `learn-meme` | 遇到看不懂的**说法**（梗、黑话、缩写、谐音） | `COGNITION.md` |
| `learn-sticker` | 遇到看不懂的**表情包 / 梗图** | 先 `qq_save_sticker` 收藏，再写 `STICKERS.md` |
| `moegirl` | 遇到二次元 / ACG 相关的梗、缩写、角色、作品、弹幕用语，去萌娘百科查准确意思 | 不写 |
| `update-cognition` | **兼容壳**：只做一句话分诊（旧提示词 / 旧习惯还在用这个名字） | 不写 |

**分诊规则**（写在 `learn-meme` / `learn-sticker` / `message-digest` 三处）：有图 →
`learn-sticker`；只有文字 → `learn-meme`；图文都有 → 图进 `STICKERS.md`、那个词的用法进
`COGNITION.md`，两边互相写名字，不要在一个文件里写两遍；拿不准就不写。

`moegirl` 只管查：走萌娘百科的 MediaWiki 接口（`opensearch` 找条目名 → `prop=extracts`
取正文开头），**不用**全文搜索接口与条目网页（匿名调用被封、正文是脚本渲染的，实测都拿不到
东西）。弄懂之后的沉淀仍然归 `update-cognition`，所以没开长期记忆时它也能用 ——
skill 的发现归预设管，跟 `memory` 开关无关。

skill 由**预设**发现（不是宿主）：`dsh-web-app` 把宿主的 `skill-filesystem` 停掉了，
「locality 归预设管」。所以 `cordis.patch.yml` 的 `qq` 预设里挂了
`skill-filesystem` + `tool-skill`，扫的目录是 `<项目根>/.dsh/skills`、
`<项目根>/.agents/skills`、`~/.dsh/skills`，外加 `dsh-agent-preset` 随包出货的那套。
`allowTools` 里必须留着 `skill`，否则模型看得见目录却打不开。

新增自己的 skill：在 `.dsh/skills/<名字>/SKILL.md` 写一份（frontmatter 必填 `name`
与 `description`，name 要 kebab-case 且与目录同名），文件**不需要重启**就被发现。

### 认知（学梗）是怎么发生的

两条路，写进**两个文件**：

1. **聊天中按需**：遇到不懂的**说法** → `learn-meme`（写 `COGNITION.md`）；遇到看不懂的
   **图** → `learn-sticker`（先 `qq_save_sticker` 收藏，再写 `STICKERS.md`）；是二次元 /
   ACG 那一类就先按 `moegirl` 去萌娘百科查，其它话题用 `web_search`。懂之前不要装懂。
2. **摘要时自动**：定时摘要扫到新东西时按同一套分诊规则沉淀；只是又用了一次老梗就不动
   （认知库要短，长了没人读）。

**为什么分成两个文件**：它们的「键」根本不同 —— 梗是**文字写法**（所以 `qq_memory search
蚌埠` 能命中），表情包是**收藏后的文件名**（`.qq-stickers/委屈猫.gif`）。混在一起时，表情包
条目会拿 `.qq-media/<内容哈希>` 当键，而那是 LRU 缓存、迟早被淘汰，于是那条记忆变成一条
死链（真实事故：机器人说「存好了」，过几天那张图没了）。两条硬规则：

- `COGNITION.md` 里**不许出现文件路径**（`.qq-media/…`、`.qq-stickers/…` 都不行）；
- `STICKERS.md` 里**不许出现 `.qq-media`**（那说明还没收藏，先收藏再记）。

**提示词里怎么用**：`STICKERS.md` 的「已收藏」条目以「名字（含义）→ 完整路径」的形式每轮
注入（最多 40 条），模型看含义就能判断该不该发，不用先 `read_image` 猜；路径**原样给全**
（带上 `.jpg` / `.gif` 扩展名），模型抄进 `[[图片: …]]` 就行 —— 只给名字时它会猜扩展名，
猜错就是一次「那张表情我这儿没有」（真实事故：`敲盆.gif` 被写成 `敲盆.jpg`）。
`COGNITION.md` 最近 15 条「置信：确认」的条目作为「最近学的梗」注入（≤1200 字），谐音梗
不用先 search 再答。
「最近」按**首见日期**算，不按它在文件里排第几 —— 否则整理一次文件（合并标题、分节）
就等于悄悄换掉它每轮记得什么。没有日期的条目算最旧，同日期按文件顺序。
「置信：存疑」的条目**不进**提示词，只能被 `qq_memory search` 到 —— 那是给已经记下的猜测
留的余地，不是「先写一条再猜」的借口。

**怎么写入**：结构化文件只走 `qq_memory` 的 `upsert`（字段级），不要整份重写：

```
qq_memory { action: "upsert", path: "COGNITION.md", name: "蚌埠住了",
            meaning: "忍不住笑了", usage: "有人发离谱东西时",
            type: "谐音", variants: "绷不住/绷" }
qq_memory { action: "upsert", path: "STICKERS.md", name: "无语",
            meaning: "无语、懒得吐槽", image: ".qq-stickers/无语.gif" }
```

`type` 决定落在哪个二级标题：`缩写` / `谐音` / `专名`（游戏、角色、选手、作品）/ `其它`。
同名的会**原地替换**，不会多出一条；`remove` 按名字删。整份 `write` 仍然存在，但会先归一化
（重复二级标题只留一个、完全相同的行去重），并在条目数掉到 90% 以下时直接拒绝。

**从旧认知库迁移**：老部署的 `COGNITION.md` 里可能有以 `.qq-media/…` 为键的表情包条目。
`scripts/migrate-cognition.mjs` 一次性把它们迁到 `STICKERS.md`（用画面指纹认同一张被 QQ
重新编码过的图；认不出就标「原图已过期」放进「未收藏」区）：

```bash
node scripts/migrate-cognition.mjs --json            # 默认 dry-run，只看报告
node scripts/migrate-cognition.mjs --apply           # 真的写（先备份成 *.bak-<时间戳>）
node scripts/ops.mjs migrate cognition --apply       # 同一条路，走运维 CLI
```

退出码 `0` = 没什么要人处理的，`2` = 有认不出来的条目（报告里逐条列出），`3` = 脚本自己出错。

### 关掉 / 排查

```bash
# 关掉整个长期记忆（工具、skill 提示、定时器都消失）
memory: false

ls -la ~/Projects/qqbot/.qq-memory                  # 看到目录结构
cat ~/Projects/qqbot/.qq-memory/digest.json         # 上次摘要时间与条数
journalctl --user -u qqbot -f | grep 'qq-bridge: digest'        # 摘要开始 / 失败 / 超时
journalctl --user -u qqbot | grep 'qq-bridge: memory'           # 目录、定时器、启动补课
```

- **不摘要**：先看 `digestAtHour`（默认 4 点，别在下午找它）和 `digestMinLines`
  （没攒够就留到明天），再看 journal 里的 `qq-bridge: digest` 行 —— 每次真的跑摘要
  都会打一行「digest <key>: N/M lines」，每小时几点排的下一次定时器则在
  `qq-bridge: memory enabled at …` 那一行里。
- **错过了摘要点**：只要 `digestCatchUp` 没关，那个会话下次有人说话时就会补一次；
  关掉的话就要等到明天的 `digestAtHour`。
- **记忆是空的**：确认 `memoryDir` 在 `cwd` 内（配到外面只会有一条 warn 然后停用）。
- **摘要报错**：多半是预设里没有 `skill` 工具，或 `qq_memory` / `qq_transcript`
  被 `allowTools` 挡掉了（摘要 Agent 用的是同一份预设与白名单）。
- **条目「写了却没进提示词」**：那一行字段不全（少于两段），解析器只记 warn。`qq_memory read`
  的 note 会点出来，`node scripts/ops.mjs doctor` 报 `COGNITION_UNPARSED` —— 用 `upsert`
  重写那一行，别手写 markdown。
- **表情包发不出去、只收到一句「那张表情我这儿没有」**：`[[图片: …]]` 只认 `.qq-stickers/`，
  `.qq-media/<哈希>` 是入站缓存（默认 200 张，会被淘汰）。要让某张图以后能发，先
  `qq_save_sticker` 存一次。
- **想回滚一次写坏的记忆**：`.qq-memory/.history/` 里是每次写入前的旧版本（每个文件留最近 20 份）。
- **记忆文件越写越乱**：`doctor` 会报 `COGNITION_DUPLICATE_SECTION` / `STICKER_PATH_MISSING` /
  `STICKER_MEDIA_PATH`；下一次用 `upsert` 或整份 `write` 时，重复标题与完全相同的行会在落盘时
  自动合并。

## QQ 会话的工具从哪来（`agentPreset`）

在 **Web 表面**（本 profile 用的 `@deepseek-ai/dsh-web-app`）里，`bash` / `read` /
`glob` / `grep` / `web_search` / `web_fetch` 这些「agent 平面」的工具**不在宿主上**：
它们被搬进了每个 Agent 预设，只有 join 了预设的 Agent 才继承得到。直接
`ctx.agents.create()` 出来的 Agent 不 join 任何预设，于是它只有宿主平面的全局工具
——也就是本插件的 `qq_*` 那几个（发消息 / 发图 / 存表情 / 会话列表 / 记忆）。

所以插件会在 `setup()` 里先给 QQ 会话 Agent 挂一个预设，再施加 `allowTools`。
挂的是 **bundle 自带的 `qq` 预设**（声明在 `cordis.patch.yml`）：

```yaml
agentPreset: qq   # 留空 = 用部署默认预设；none = 不挂
```

`qq` 预设只放五样东西：`tool-fs`（read / read_image / write / edit）、
`tool-fs-search`（glob / grep）、`tool-web`（web_search / web_fetch）、
`skill-filesystem` + `tool-skill`（发现并加载 `.dsh/skills` 下的 skill）、以及压缩
（compaction / tool-result-pruner）。没有 shell、没有子代理、没有 workflow、没有计划模式。

预设里的 `compaction-basic` **显式钉了压缩门槛**（`thresholdRatio: 0.06` /
`retainRatio: 0.02`：上下文到约 6 万 token 就把最老的一段压成 checkpoint，逐字保留
最近约 1.5 万）。不配的话，默认门槛是 `min(上下文×0.8, 上下文−请求 maxTokens−headroom)`
—— deepseek-flash 声明 100 万上下文，算下来约 **67.8 万 token** 才会触发，而 QQ 会话
是长驻的（一个群一个会话，重启还在，只有 `/reset` 才开新一轮），永远到不了那个量级。于是历史
只增不减，**每一轮都把整段历史重发一遍**，上下文越大每轮越贵。压到 6 万之后单轮上下文
才有上限；觉得它记事不够就往上调，想更省就往下调（`retainRatio` 必须小于 `thresholdRatio`）。

**为什么不直接挂 `standard`**（踩过的坑）：

- `standard` 的 `subagent` 行开了 `modelSelectionSettings: true`。这个模式下
  `dsh-tool-subagent` 会在每个 Agent 创建时通过 `agent.ctx.inject(...)` **在 Agent
  自己的作用域里**再注册一份 `subagent` 工具。而 `tools.restrict()` 按设计只收窄
  **继承来的**工具，放过「该作用域自己的注册」（那是给 Agent 作答所依赖的机制留的口子），
  于是 `subagent` 会绕过 `allowTools` 出现在 QQ 会话的工具表里。
  同一预设里的 `subagent_fork` / `workflow` 是普通注册，反而被白名单挡住了
  —— 只有走 per-agent 注册路径的那个漏出来。
- `standard` 还带了 bash / write / subagent / workflow / ask_user / plan-mode 等一大
  堆 QQ 用不到的东西。**能力面应该在组合层面收窄**，而不是先给全量、再指望白名单兜住。

其它要点：

- 顺序是**先挂预设，再收窄**：`tools.restrict()` 只能收窄这个 Agent **继承得到**的
  工具，白名单给不出它本来就没有的能力。
- `allowTools` 是第二层：预设里的 `write` / `edit` 就靠它挡掉（它们在预设层，属继承工具，
  收得掉）。
- 从 `dsh-base` 起的组合（如 headless）根本没有预设平面，`ctx.get('agentPresets')`
  取不到东西，插件会跳过挂载、直接收窄宿主工具，行为与老版本一致。

**排查「QQ 会话突然不能联网 / 读文件」**：插件的日志会直接写在进程的 stderr 上
（systemd 收进 journal），所以：

```bash
journalctl --user -u qqbot -f | grep qq-bridge
```

- `qq-bridge: … joined agent preset qq` —— 预设挂上了，工具存在。
- `qq-bridge: … limited to tools: read, …, web_search, …` —— 白名单**完整**生效。
- `qq-bridge: allowTools rejected (...); keeping only the visible names: … — a whitelist
  cannot grant tools this Agent does not have` —— 白名单里有这个 Agent 拿不到的名字
  （没挂预设、预设里没有该工具，或名字拼错）；冒号后面列出的就是真正生效的那几个。
- `qq-bridge: could not resolve agent preset "…"` —— 预设名不存在或激活失败（原因跟在
  后面）。这种情况下 QQ 会话会退化成只有 `qq_*` 那几个工具。

> 为什么要自己写 stderr：这个部署没有把 cordis 的 logger 接到 stdout/stderr 上
> （`ctx.logger.warn` 只进内存缓冲与 OTel），只调 `ctx.logger` 的话 journal 里
> 一个字都看不到。插件因此每条日志都镜像一行到 stderr。

## 限制 QQ 会话的工具（`allowTools`）

QQ 那头是**不可信输入**：谁都能给机器人发消息，而这个机器人背后是一个能读写
文件、跑命令的 Agent。`approvalPolicy: never` 只挡住了「需要审批」的操作，
`allowTools` 是把能力面收窄的第二层。

```yaml
allowTools:
  - read          # 只读文件
  - qq_send_message
```

- **只影响 QQ 会话**：收窄施加在「由 QQ 消息创建出来的那个 Agent」自己的作用域上
  （DSH 的 `tools.restrict()`），Web UI 主会话等其它 Agent 完全不受影响。
- **空 = 不限制**，与 `allowUsers` / `allowGroups` 一致；填了才生效。
- 过滤的是**继承来的**工具（宿主平面的全局工具 + 这个 Agent join 的预设里的工具）。
  ⚠️ Agent **自己作用域里注册**的工具不受影响 —— 这是设计使然（它回头作答所依赖的
  机制不能被收走），但也意味着某个预设行可能绕过白名单，典型例子就是 `standard`
  预设下开了 `modelSelectionSettings` 的 `subagent`（见上一节）。要收紧能力面，
  **换一个更小的预设**，别指望 `allowTools` 兜底。
- 白名单只能**收窄**，不能**授予**：列了 `web_search` 但预设里没有 `tool-web`，
  结果就是该工具不存在，会被当成不认识的名字丢掉 —— 见上一节。
- 名字写错时不会拖垮对话：不认识的名字会被丢掉并打一条 `warn` 日志；如果一个都
  不认识，该会话将被收走全部工具（fail-closed —— 你明确要的是白名单，不能悄悄
  退回全量工具）。
- 提示词会跟着联动：没被放开的 `qq_*` 工具不会再出现在渠道说明里。
- 生效时机是**创建/恢复 Agent 时**。已经在跑的 QQ 会话 Agent 不会被追溯，
  改完配置要重启 Harness 进程才作用于已有会话。

⚠️ 别把「能开出新 Agent」的工具放进白名单：`subagent`、`workflow`、`run_code`
这类工具会启动**自己的**工具集，不再受这张白名单约束。要收紧能力面，就把它们
留在白名单之外。同理，`run_code` 是 PTC 模式（`tools.mode: ptc/both`）自带的
传输工具、无法被列进白名单，但它能调到的子工具仍然受白名单约束。

## 新开一轮会话（`/reset`）

在 QQ 里**单独发送** `resetCommand`（默认 `/reset`）即可给**当前这个会话**开新的一轮：

- 只影响发指令的那个会话（私聊对象 / 群），别的会话不受影响；
  群聊的上下文缓冲（`ambientMessages`）也一起清掉。
- 整条消息恰好等于指令才触发；`/reset 你好` 这种带内容的消息会照常交给 Agent。
- **只有 `resetUsers` 里的 QQ 号能重置**，而且这一项**默认是空的 —— 也就是谁都不能**。
  这一条与 `allowUsers` 的「留空 = 不限制」刻意相反：群消息是不可信输入，一个「没配就等于
  人人可用」的重置指令意味着群里任何一个人都能悄悄把会话重开一轮，而且默认没人会去配它。
  所以想用这个指令必须显式写号。本仓库的写法是把号放进**环境变量**（DSH 启动时会读
  `<启动 cwd>/.env` 和 `$DSH_HOME/.env`）：

  ```bash
  # <仓库根>/.env（已被 .gitignore 盖住）
  QQBOT_RESET_USERS=123456789,987654321
  ```

  `cordis.patch.yml` 里那行 `resetUsers: !!js …` 会把逗号分隔的变量拆成数组、去空白，
  变量不存在或为空时就是空数组（= 谁都不能，与默认值一致）。**改完要重启进程**（`.env`
  只在启动时读一次）。也可以在 Web UI 的插件设置里直接填 `resetUsers` —— 那边写的是完整
  config；但别去 profile 的 `cordis.patch.yml` 里单写这一个字段（见[配置项](#配置项)开头的警告）。
  群里看的是**发言者**的 QQ 号（不是群号）；私聊看的是对方。
- **没权限的人发 `/reset` 会被静默忽略**：不重置，也不回一句「你没有权限」—— 回话等于告诉
  全群这里有这么个指令、还激人去试。这条消息仍然照常记进转录（留痕在长期记忆里），但不会
  交给模型，也不会把当时攒着的那批消息提前投出去。
- 启动日志里会明说权限状态（`reset command "/reset" is allowed for 1 account(s): …` /
  `… is disabled for everyone: resetUsers is empty`）—— 配错了不用猜。
- **`/reset` 不是「删掉会话」，而是「换一个会话重新开始」**：先销毁活着的 Agent
  （连同它内存里的上下文与 Session 写出句柄），再把「这个会话开到了第几轮」+1
  并落盘。下一条消息据此算出一个**新的** Session id，于是从头开始。
- 上一轮的 Session 记录**留在磁盘上**当那段聊天的存档，不会被删；只是不再被带进
  新一轮的上下文里。想真删掉它是运维动作（删 `$DSH_HOME/sessions/<项目>/<会话 id>/`），
  不是聊天指令 —— 聊天里没有「把说过的话抹掉」这种能力。
- 「第几轮」是落盘的，所以**重启不会把上一轮 resume 回来** —— 否则 `/reset` 等于白按。
  标记文件在会话根目录下的 `reset/<会话>.json`（拿不到会话根时退回 `cwd` 下的
  `data/reset/`）。
- `qq_list_conversations` 里报的 `session_id` 会换成新一轮的 id，`session_round`
  是当前轮次（0 = 从没 `/reset` 过）。
- 长期记忆（`.qq-memory/`）**不受影响**：转录、`MEMORY.md` 是按会话 key 落的，
  与轮次无关 —— 「上一轮聊过什么」仍然记得，只是不再占着上下文。
- 把 `resetCommand` 设为空串即可禁用该指令。

## 每天轮换 API key（`apiKeyRotate`）

一个 key 用得久了会碰到额度、限流或者单纯的「今天不太对劲」。这一节让它**每天凌晨 4:00
自己换一把**：从你自己的 key 池里挑下一个**现在真的能用**的，写进 Harness 的凭据文件。

**它换的是哪个 key**：`apiKeyRef`（默认 `DEEPSEEK_API_KEY`）—— 也就是 QQ 会话和 Web UI
调模型时用的那一个。插件不碰别的东西。

**key 池怎么建**：`apiKeyFile`（默认 `data/api-keys.txt`，相对 `cwd`，已在 `.gitignore` 里）
是一个纯文本文件，一行一个 key：

```text
# data/api-keys.txt —— 一行一个 key，`#` 开头的行是注释
sk-aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa
sk-bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb
# 备注也可以单独写一行
sk-cccccccccccccccccccccccccccccccc
```

池子的顺序**就是轮换顺序**：每次从「当前正在用的那个 key」的下一个开始，绕回开头。
当前 key 不在池子里（手工填的、或者池子刚调整过）时从第一个开始。文件不存在、还没填 key、
或者池子里只有当前这一个 —— 都什么都不做，只在日志里说一句该怎么办：

```text
qq-bridge: api key rotation (daily at 04:00): no key pool at data/api-keys.txt; put one key per line there to start rotating
```

**「尝试」体现在探测上**：候选 key 会先用 `apiKeyProbeUrl`（默认
`https://api.deepseek.com/models`）GET 一下，**2xx 才算可用** —— 这个探测不消耗 token。
探测不过就试池子里的下一个；全都不通过就**保留原来的 key**，只记一条 warn。所以池子里
混进一把失效的 key 不会把 bot 换成不可用的状态，也不会每天卡在同一行上：

```text
qq-bridge: api key rotation: candidate sk-bbb…#3f2a91cd rejected (HTTP 401); trying the next one
qq-bridge: api key rotation: switched DEEPSEEK_API_KEY from sk-aaa…#d1c0be27 to sk-ccc…#9ab41f02 (HTTP 200)
```

几个行为细节：

- **立刻生效，不用重启**：Harness 的模型调用是每次请求都去解析凭据的，本地凭据层又是
  监听文件的，所以换完当场就用新的；正在跑的那一轮不受影响。
- **改的是 `$DSH_HOME/.credentials.yaml` 这一个全局凭据**，而这个文件是所有 profile
  共用的 —— 也就是说它同时影响 Web UI。这是有意的（一把 key 通吃），但值得知道。
- **key 来自启动环境时不换**：如果 `DEEPSEEK_API_KEY` 是从 shell / `EnvironmentFile`
  传进来的，它的优先级高于凭据文件，写文件不会生效 —— 那种部署下插件只记一条 warn 说明
  原因，而不是每天假装换成功。
- **key 来自 `<cwd>/.env` 或 `$DSH_HOME/.env` 时照换**：凭据文件排在它们前面，写进去有效。
- **`apiKeyRotateHour` 只是「几点试一次」**，不落盘「今天换过没有」：重启不会导致当天换
  两次（定时器每次都算「距下一个整点还有多久」），但如果这个时刻正好在重启、那一轮就跳过，
  第二天再换。
- **日志里永远看不到完整的 key**：只打前 6 个字符 + 内容摘要前 8 位，例如
  `sk-aaa…#d1c0be27`。
- 想关掉：`apiKeyRotate: false`（启动日志里会写 `api key rotation is off`）。
  想验证一次而不用等到凌晨 4 点：把 `apiKeyRotateHour` 设成**下一个整点**，重启即可
  （定时器每次都按「距下一个整点还有多久」排期）。

## 工具

| 工具 | 作用 |
|---|---|
| `qq_send_message` | 向指定 QQ 号（私聊）或群号（群）发送文本，超长自动分段；正文里可以写 `[[@昵称]]` / `[[@全体成员]]` @ 人（见「像真实群友一样说话」的第 6 条） |
| `qq_send_image` | 向指定 QQ 号或群发一张图 / 表情包：来源是 `cwd` 里的图片路径（含 `.qq-stickers/…`、`.qq-media/…`）或一个 http(s) 图片链接；从 QQ 会话里调用时默认发回当前会话 |
| `qq_save_sticker` | 把一张图**存进表情包目录**（`.qq-stickers/<名字>.<真格式>`）变成以后能挑的表情：来源同上，名字会被清洗成单层文件名、同名不覆盖、张数受 `stickerMaxFiles` 限制；图片本身不可用（目录没配 / 配到 `cwd` 外）或白名单没放开时**根本不注册** |
| `qq_list_conversations` | 列出在线群/好友列表，以及本 Harness 已处理过的 QQ 会话、当前 Session id 与轮次（`session_round`） |
| `qq_transcript` | 读某个 QQ 会话的聊天记录：`list` / `read` / `search`（长期记忆的原料，见[长期记忆](#长期记忆聊天记录--摘要--认知)） |
| `qq_memory` | 读 / 追加 / 覆盖 / 搜索 / **逐条 upsert / remove** 长期记忆文件：`conversations/<slug>/MEMORY.md`、`COGNITION.md`、`STICKERS.md`、`INDEX.md`；整份 `write` 有「条目数不能掉 10%」护栏，写前留 `.history/` 备份；写被限制在 `memoryDir` 之内 |

这六个都是纯宿主平面的全局工具，所有 Agent（包括 Web UI 里的主会话）都能用。
`qq_send_image` / `qq_save_sticker` 见[它也能发表情包](#它也能发表情包)；
`qq_transcript` / `qq_memory` 见[长期记忆](#长期记忆聊天记录--摘要--认知)，
关掉 `memory` 后它们**根本不会注册**。

## NapCat 端要求

NapCat 需要开启一个 **WebSocket 服务器**（不是 websocketClients）。
在 NapCat WebUI 的「网络配置」里新建 WebSocket 服务器，端口与本插件
`endpoint` 一致；若设了 token，同步填到 `accessToken`。

当前这份配置对应的容器：

```
容器     napcat (mlikiowa/napcat-docker:latest)
端口     3001  → OneBot WebSocket 服务器（name: qqbot, token 为空）
配置文件 /app/napcat/config/onebot11_<QQ号>.json
```

查看配置：

```bash
docker exec napcat cat /app/napcat/config/onebot11_100000000.json
```

**Windows 桌面版不是这套**：那边 NapCat 是注入进本机 QQ 的原生进程（没有容器、没有 docker
网桥），配置在 `<NapCat>\config\onebot11_<QQ号>.json`，而且有脚本代劳 —— 见
[Windows 桌面版](#windows-桌面版napcatshell)。

## 运行方式：独立的 `qqbot` profile

插件装在专属 profile 里，和日常用的 `web` profile 完全隔离。

```
profile   ~/.dsh/profiles/qqbot/         （从 dsh 自带的 web 模板克隆）
bundles   @deepseek-ai/dsh-base
          @deepseek-ai/dsh-web-app
          @qqbot/dsh-plugin-qq
依赖      @qqbot/dsh-plugin-qq -> link:<本仓库的绝对路径>   （`link:` 不认 `~`）
UI        http://127.0.0.1:3081/
```

启动：

```bash
dsh --profile qqbot --port 3081 --no-open
```

没有"常驻但无 UI"的官方模板可用（`headless` 是一次性任务，`acp`/`sdk` 是
stdio JSON-RPC 服务），所以从 `web` 模板克隆：进程常驻，并且可以顺便在
浏览器里实时看 QQ 会话。

### 常驻运行

**不要**把它挂在一个 agent 会话的后台任务里：DSH 的 bash 工具跑在
`bwrap --die-with-parent` 沙箱内，沙箱一销毁子进程就跟着死。常驻必须由你
自己的登录会话或 systemd 托管。仓库里备好了 user unit：

```bash
cp deploy/qqbot.service ~/.config/systemd/user/     # 在仓库根目录执行
systemctl --user daemon-reload
systemctl --user enable --now qqbot

systemctl --user status qqbot          # 状态
journalctl --user -u qqbot -f          # 日志（含带 token 的 Web UI 地址）

# 想让它在没有桌面登录时也能跑：
loginctl enable-linger "$USER"
```

`Restart=always`，崩了 5 秒后自动拉起。改完源码后
`systemctl --user restart qqbot` 即可（等价于"重启 Harness"）。

临时手动跑（放 tmux 里，别用 agent 的后台任务）：

```bash
tmux new -s qqbot 'dsh --profile qqbot --port 3081 --no-open'
```

### 凭据

QQ 会话用的模型是 `deepseek-official/deepseek-flash`（继承 `dsh-base` 的
`agent-default-model` 默认值），它需要 `DEEPSEEK_API_KEY`。解析顺序是：

```
继承的环境变量
  > $DSH_HOME/.credentials.yaml
    > <启动 cwd>/.env
      > $DSH_HOME/.env
```

注意 Harness 会用 `scrubbedParentEnv` 把敏感变量从**所有子进程**里抹掉，
所以 `env` 里看不到它属于正常现象。如果从没有该变量的环境启动（systemd、
别的 shell、CI），会报 `MISSING_CREDENTIAL`。

**推荐做法**：在 3081 的 Web UI 里打开 Models 页面填一次 key。它写入全局的
`$DSH_HOME/.credentials.yaml`，之后任何 profile、任何启动方式都不再依赖 shell 环境。
从自己的 `~/.zshrc`（已 export 该变量）里启动也可以，但只在那一个 shell 有效。

> 想让它每天自己换一把 key（额度 / 限流用），见[每天轮换 API key](#每天轮换-api-keyapikeyrotate)。
> 注意那条路径写的就是上面这个 `$DSH_HOME/.credentials.yaml`，而且要求 key 是**存在文件里**
> 的（从启动环境传进来的 key 优先级更高，轮换写不进去，插件会说明并跳过）。

## Windows 桌面版（NapCat.Shell）

桌面版 DSH（Electron）与 NapCat 跑在**同一台 Windows 机器**上，形态和上面那套「容器 +
systemd」完全不同：没有 docker 网桥、没有 `systemctl`、Host 进程的 cwd 是 DSH 的 profile
目录。仓库里备了一个一键脚本，把**两边**一起配好。

### 照着走一遍（第一次装就按这个顺序）

1. 解压发布包到**你想长期放着的位置**（比如 `D:\dsh-qq-bridge-0.2.0`），以后别再挪：
   profile 里存的是指向这个目录的链接，挪了要重跑一次脚本（脚本会自己发现并重建链接）。
2. 双击 `scripts\napcat-setup.cmd`（或跑 `node scripts\napcat-setup.mjs`）—— 它配好 NapCat
   的网络配置、profile 的 `.env`，并把插件装进 `desktop` profile。想先看它要做什么就加
   `--dry-run`；知道自己机器人的 QQ 号就带上 `--qq <号>`，它会顺手写好快速登录。
3. 启动 NapCat 扫码登录：`scripts\napcat-setup.cmd --start --window normal`
   （**第一次要看得见窗口**才能扫二维码）。登完确认它能正常监听端口。
4. **再跑一次脚本**（同第 2 步的命令）—— 这一步是必须的：`config/onebot11_<QQ号>.json`
   与 `config/webui.json` 都是 NapCat **第一次启动时**才生成的，第二次运行才能把
   WebSocket 服务器那一条对齐、并写进 `autoLoginAccount`。
5. 重启 DSH 桌面版（源码在启动时加载，装完必须重启）。
6. 在 DSH 的 **Models** 页面确认模型凭据已填。
7. 私聊机器人发一句话，它在 QQ 里回你就说明整条链路通了。
8. （可选，推荐）`scripts\napcat-setup.cmd --autostart install`：以后开机静默启动，
   没有那个黑框框、也不再问 UAC。见[不要那个黑框框](#不要那个黑框框推荐做法)。

命令清单（第 2 / 4 步用的就是前两条）：

```powershell
# 在仓库根目录（或者直接双击 scripts\napcat-setup.cmd）
node scripts\napcat-setup.mjs --dry-run      # 先看它打算做什么：一个字都不写
node scripts\napcat-setup.mjs --qq 123456    # 指定机器人账号（还没登录过也能先写好配置）
node scripts\napcat-setup.mjs                # 真配
node scripts\napcat-setup.mjs --start        # 顺手启动 NapCat（提权 + 快速登录，窗口默认最小化）
node scripts\napcat-setup.mjs --autostart install  # 装计划任务：以后开机静默启动，没有黑框框、也不再问 UAC
node scripts\napcat-setup.mjs --autostart status   # 看它装没装、上次跑成没成
node scripts\napcat-setup.mjs --autostart remove   # 不想要了
node scripts\napcat-setup.mjs --where        # 只回答「用的是哪份 node」，排查用
```

> **不装 Node 也能跑**：`scripts\napcat-setup.cmd` 会按「PATH → `DSH_DESKTOP_NODE_EXECUTABLE`
> → 桌面版安装目录里自带的那份 Node」的顺序找解释器，找到了就直接用它跑 `.mjs`；
> 桌面版自带的是完整的一份 Node（实测 v24.x），所以新机器上不需要先装 Node。
> 一个都没找到时它会把确切路径的写法打出来，`--where` 则随时能告诉你现在用的是哪一份。

它做五件事，每一步都是**幂等 + 先备份**：

1. **NapCat 的网络配置**：在 `<NapCat>\config\onebot11_<QQ号>.json` 里写好（或对齐）一条
   监听 `endpoint` 端口的 WebSocket 服务器 —— `name: dsh-qq-bridge`、`enable: true`、
   `reportSelfMessage: false`、`messagePostFormat: array`、token 与 `accessToken` 一致。
   **只动 `websocketServers` 里我们那一条**：用户自己调过的 `debug` / `heartInterval`、
   以及 `httpServers` / `websocketClients` / `timeout` 全部原样保留；改之前把原文件复制成
   `onebot11_<QQ>.json.bak-<时间戳>`。已经配好时**一个字节都不写**（连备份都不产生）。
   > NapCat 目录怎么找：`config/onebot11_<QQ号>.json` 是**登录之后**才生成的，所以
   > 「刚解压、还没登录过」的 NapCat 也认（判据是目录里它自带的 `launcher*.bat` /
   > `napcat.mjs`）—— 发布版安装流程正是这一种，不然 `--qq` 那条路永远走不到。
2. **快速登录**（只在显式给了 `--qq` 时）：把 `<NapCat>\config\webui.json` 的
   `autoLoginAccount` 设成这个号，NapCat 以后启动就自己快速登录，不用每次掏手机扫码。
   同样只动那一个字段、先备份；`webui.json` 还不存在（NapCat 没启动过）时**不凭空造**它，
   而是提示你登录完再跑一次。不想要这条就加 `--no-auto-login`。
   > 快速登录的前提是本机已经为这个号留下过登录记录；没有记录时 NapCat 会退回二维码 ——
   > 那不是失败，扫一次码，之后才会走快速登录。
3. **profile 的 `.env`**：把 `QQBOT_ENDPOINT` / `QQBOT_ACCESS_TOKEN` / `QQBOT_CWD` /
   `QQBOT_NAPCAT_DIR` 写进 `~/.dsh/profiles/desktop/.env` 里一段带标记的段落，段落**之外**
   的内容一个字节都不动。这些取值由 `cordis.patch.yml` 里的 `!!js process.env.QQBOT_*`
   读进配置 —— 「每台机器不一样的值」全走 `.env`，仓库里那份 patch 保持所有部署共用。
   （`#` 是 `.env` 的注释符，取值里别出现它。）
4. **装进 desktop profile**：`package.json` 里加 `"@qqbot/dsh-plugin-qq": "link:<仓库>"`，
   并把它追加进 `dsh.profile.bundles` —— **两处都必须有**，只加依赖不加 bundles 等于
   「装上了但不加载」；再在 `profiles/desktop/node_modules/@qqbot/dsh-plugin-qq` 建一个指向
   仓库的链接（Windows 上用 junction，不需要开发者模式）。原 `package.json` 先备份成
   `.bak-<时间戳>`。
   > 链接**已经存在**时会读一眼它指着谁（junction 也能读）：指着别的目录（上一份发布包、
   > 旧的 clone）就删掉重建，并把你原来指向哪也打出来。「存在就当装好了」是不行的 ——
   > 解析实际走链接，于是会出现「manifest 写的是新路径、加载的是旧代码」而**一句报错都没有**。
   > 目录里那个东西如果**不是链接**（例如你手工拷了一份插件进去），脚本不删它，只提醒你
   > 现在加载的是它、不是本仓库。
5. `--start` 时启动 NapCat：**以管理员身份**（UAC 弹窗点「是」）跑官方文档让双击的那个
   `launcher.bat`，并把 `--qq` 当 `-q <号>` 传进去让它快速登录。窗口样式由 `--window` 决定：
   `normal` / `min`（默认，最小化、不挡视线）/ `hidden`（无窗口，走的是另一套机制，见下）。
   **首次登录要扫二维码，得能看见窗口**，所以第一次请用 `normal` 或 `min`。

### 不要那个黑框框（推荐做法）

> **那个黑框框就是 NapCat 本体**：关掉它 = 停掉机器人，它不是「一个可以随手关掉的日志窗口」。
> 想让它彻底消失，三条路，按推荐程度排：

| 这条路 | 适合谁 | 代价 |
|---|---|---|
| `node scripts\napcat-setup.mjs --autostart install` | 大多数人 | 装的时候点一次 UAC；以后开机**静默**启动，没有窗口、也不再问 UAC |
| 官方 [NapCat.Windows 可视化管理工具](https://github.com/NapNeko/NapCatQQ-Desktop) | 想要图形界面 / 多账号的人 | 多装一个 EXE（单文件、托盘托管、后台静默） |
| `--start --window min`（默认） | 只想最小化、不想动系统设置 | 任务栏里仍然有一个 NapCat 的控制台 |

**为什么不能简单地「隐藏窗口」**：`launcher.bat` 发现自己不是管理员时，会用
`launcher-elevate.ps1` **把 `wt.exe`（Windows Terminal）提权起来**再重跑自己 —— 而 Windows
Terminal 根本没有「隐藏启动」这回事，那个窗口一定会出现。所以 `--window hidden` 走的是另一条
路：提权跑 `wscript.exe`（GUI 子系统程序，自己不带控制台），由它用 `WshShell.Run` 的窗口样式
`0`（SW_HIDE）去起 `cmd.exe /s /c "launcher.bat" -q <号>` —— 控制台**从创建那一刻**就是隐藏的。
三个细节都是踩出来的，别顺手改：

- **必须 `wscript.exe //B`**：不加 `//B` 时 WSH 一出错就弹一个模态错误框停在那儿等人点，
  而我们连窗口都没有 —— 表现是「机器人静默停住、日志里什么都没有」（本地实测：同一份脚本
  加 `//B` 跑通，不加就是卡住等点）。
- **命令行走 `cmd.exe /s /c`，而不是把 `.bat` 直接交给 WshShell.Run**：后者走文件关联
  （ShellExecute），从下载来的 zip 里解压出来的 `.bat` 带 Mark-of-the-Web，会弹「打开文件 -
  安全警告」等人点 —— 同样是我们看不见的卡死。
- **包装脚本按 UTF-16LE + BOM 落盘**：WSH 读没有 BOM 的脚本时按系统 ANSI 解码，注释和中文
  路径会变成乱码。

`--autostart install` 做的是一次性注册一个计划任务（名字 `dsh-qq-bridge-napcat`）：

- **登录时触发 + 以最高权限运行（`RunLevel: HighestAvailable`）**：不提权 QQ 会崩在
  `QQNT.dll`（见[下一节](#为什么必须提权启动实测)），而计划任务让「提权」不再需要每次点 UAC
  （`schtasks /run` 直接以最高权限起来）。
- **`LogonType: InteractiveToken`**：必须跑在**用户会话**里。NapCat 要拉起 `QQ.exe` 并注入，
  「不管用户是否登录都运行」会把进程扔进会话 0，那里 QQ 根本起不来。
- **`MultipleInstancesPolicy: IgnoreNew` + `ExecutionTimeLimit: PT0S`**：不许起两份（抢同一个
  QQ 和端口），也不许跑满默认的 72 小时被掐掉。
- 装的时候顺手把 NapCat 的日志改成**写文件**（`config/napcat.json` 的 `consoleLog=false` /
  `fileLog=true`，先备份、幂等，`--no-log-to-file` 可关）：窗口看不见了，日志是唯一的现场，
  落在 `<NapCat>\logs\<时间戳>.log`（NapCat 自己按 5MB × 5 个轮转）。
- 脚本会把 **WebUI 的地址与 token** 打出来（从 `config/webui.json` 读）。它是隐藏之后唯一
  还看得见的「控制台」：**看日志、扫码登录、改配置都在那里** —— NapCat 的 WebUI 自带登录页
  与二维码，所以「窗口藏起来就没法第一次扫码」并不成立。token 原本是打在控制台里的，现在从
  那个文件里读给你。
- 停止：`schtasks /end /tn dsh-qq-bridge-napcat`（必要时再跑一次 `<NapCat>\KillQQ.bat`）。
  卸载：`--autostart remove`。

**第一次登录仍然建议先看得见**：脚本在 `config/webui.json` 还不存在时（= 这份 NapCat 从没
启动过）会**拦住** `--autostart install`，让你先跑一次 `--start --window normal` 扫码 ——
那时既没有二维码可看、WebUI 也还没生成，隐藏启动等于把自己关在门外。知道自己在做什么就加
`--force`（例如你打算装完再从 WebUI 登录）。

> 在 DSH 自己的沙箱里跑这个脚本时，`schtasks` 与 CIM 会被拦下（实测报「无法从客户端中访问
> CIM 资源」/「系统找不到指定的路径」）。**注册计划任务这一步请在普通终端里跑**（双击
> `scripts\napcat-setup.cmd` 也算）。

`--dry-run` 与真跑共用同一条代码路径，所以试运行的输出就是真会发生的事。脚本**不碰**
`~/.dsh/.credentials.yaml`：模型凭据仍然在 DSH 的 Models 页面里填一次。

### 为什么必须提权启动（实测）

NapCat 官方文档让用户双击的是 `launcher.bat` —— 包里那几个启动器里，它是**会自己提权**的
那个（`launcher-user.bat` 是刻意不提权的变体）。这不是洁癖，是一次实测的结论：

| 启动方式 | 结果 |
|---|---|
| `launcher-user.bat`（普通用户） | 注入其实**成功**了（崩溃转储的模块列表里能看到 `NapCatWinBootHook.dll` 已加载、QQ 的 Node 运行时 `major.node` 也在），但 QQ 随后在 `QQNT.dll` 里撞 `0x80000003`（STATUS_BREAKPOINT）当场死掉，控制台只剩一句 `Process exited.` |
| `launcher.bat`（管理员） | 正常起来：登录、监听端口、插件接上，全对 |

当时的组合是 QQ 9.9.35-52892 + NapCat 4.18.38，而 NapCat 自己的 `qqnt.json` 与兼容表都覆盖
这个 build（`9.9.35-52892-x64` 的发包/收包 RVA 都在表里），QQ 的安装目录也干净 —— 没有
`loadNapCat` 之类的改动痕迹。所以这**不是**「QQ 版本不受支持」或「装坏了」。

排查用的两处证据：崩溃转储在 `%LOCALAPPDATA%\CrashDumps\QQ.exe.*.dmp`（minidump 头部的
模块列表能看出注入到底成没成），系统事件日志里则是 `APPCRASH / QQNT.dll`。

`--start` 因此走「我们自己提权」（`Start-Process -Verb RunAs`），而不是 `cmd /c start`。
看到 `Process exited.` 时先确认启动器是提权跑的那个，再看系统事件日志里的 `APPCRASH` 落在
哪个模块。要连窗口一起免掉（也不再一次次点 UAC），装[计划任务](#不要那个黑框框推荐做法)。

### 装进 `desktop` profile 的四个代价（都处理掉了）

| 代价 | 怎么修的 |
|---|---|
| QQ 会话可能继承 desktop 的默认预设（`standard`，带 shell / 子代理 / write） | 本 bundle 自带 `qq` 预设，`cordis.patch.yml` 里写死 `agentPreset: qq`，所以 QQ 会话拿到的仍然只是「只读文件 + 检索 + 联网 + 本地 skill」；`allowTools` 再收一层。换 profile 不影响这条 |
| 媒体 / 表情包 / 记忆会写进 `~/.dsh/profiles/desktop` | 桌面版是拿 profile 目录当 Host 进程的 cwd 的。脚本写的 `QQBOT_CWD`（默认 `~/.dsh/qq-bot`）把这三个目录挪到一个干净、独立的地方（它们必须落在 `cwd` 内，否则各自记 warn 并停用） |
| `@deepseek-ai/schemastery` / `dsh-tools` / `dsh-llm` 的解析 | 按 DSH 的解析规则，link 安装的插件是「linked root」，宿主那份包**只有声明成 `peerDependencies` 才会被用上**；`package.json` 里因此声明了这三个 peer。不声明的话会去用仓库里那份副本，于是宿主与插件各持一个实例（工具注册、消息构造都会开始出怪问题） |
| 改了代码不生效 | Loader 按 URL 缓存插件模块：装完 / 改完源码必须**重启整个桌面版**（停用启用插件没用）。只有 `cordis.patch.yml` 的配置改动能热生效 |

### NapCat 自检与「它为什么不说话」

插件启动时会读一眼 `napcatDir` 下的配置，**默认只读**：

- 一切正常 → 一句 info（`napcat: … 里已经有监听端口 3001 的 WebSocket 服务器`）；
- 缺那条服务器 / 端口不对 / 没启用 / token 不一致 → 一条 warn，把**原因**和修法一起写出来，
  例如 `napcat: 没有配置任何 WebSocket 服务器（缺一条监听 3001 的）；跑 node scripts/napcat-setup.mjs …`；
- `napcatAutoConfig: true` 时才动手写，写完提示**要重启 NapCat 才生效**。

找不到 NapCat 目录时只记一句 info（容器部署里它压根不在这个文件系统上，那不是错误）。
`token` 不一致是最容易查半天的一种：WS 连上又立刻被拒，而日志里只有一句 `closed`。

控制台里出现 **`Process exited.`**（QQ 刚起来就退了）是另一类问题，**不在插件能报的范围内**：
十之八九是启动方式不对 —— 没用提权的 `launcher.bat`，见
[为什么必须提权启动](#为什么必须提权启动实测)。判断顺序是先确认启动器，再看系统事件日志里的
`APPCRASH` 落在哪个模块：落在 `QQNT.dll` 就是注入/兼容那半边的事，与插件配置无关。

### 目录、配置与文件都在哪

```
DSH profile   ~\.dsh\profiles\desktop\         （Electron 独占；插件与 .env 都装在这里）
profile .env  ~\.dsh\profiles\desktop\.env     （QQBOT_* 那一段由脚本维护）
NapCat         <你解压的位置>\NapCat.Shell\     （仓库根目录下放一份也行，脚本会自动探测）
NapCat 配置    <NapCat>\config\onebot11_<QQ>.json
QQ 会话数据    ~\.dsh\qq-bot\                   （QQBOT_CWD：.qq-media / .qq-stickers / .qq-memory / data）
```

### 「装完了，但它一句话都不说」

按这个顺序查，前两步能盖住绝大多数：

1. **DSH 启动日志里有没有这句话**：`skipping profile bundle "@qqbot/dsh-plugin-qq": cannot
   resolve profile bundle …`。有它 = 插件**静默跳过**（DSH 照常启动，群里当然没反应）：
   `node_modules\@qqbot\dsh-plugin-qq` 那个链接没了、或者指着一个已经被你删掉/挪走的目录。
   重跑一次 `scripts\napcat-setup.cmd` 就会重建链接（它会读链接现在指着哪）。
   注意：`package.json` 里的 `link:` 那行**不决定**加载什么，链接才决定。
2. **`.env` 改动生效了没有**：`.env` 只在 DSH 启动时读一次，改完必须重启整个桌面版。
3. 再往下是 NapCat 那一侧：见[为什么它不说话](#napcat-自检与它为什么不说话)。

## 一键运维（`node scripts/ops.mjs`）

三套部署（Linux systemd / Windows 桌面版 / 容器里的 NapCat）共用一条命令。它是给**人和
agent** 一起用的：`--json` 时 stdout 只有一个对象，`schema: 1` 是协议版本号。

```bash
node scripts/ops.mjs doctor --json            # 我现在到底哪儿坏了？
node scripts/ops.mjs status --json            # 在跑吗？连上了吗？最后 20 行日志
node scripts/ops.mjs doctor --fix             # 只做 cwd 内的事（建 data/、写 .env.example）
node scripts/ops.mjs logs -n 200              # journalctl / 日志文件 / docker logs，按平台
node scripts/ops.mjs restart                  # systemd 重启；Windows 只重启能独立管理的部分
node scripts/ops.mjs install --apply          # 写 unit / 计划任务 / profile（默认只给计划）
node scripts/ops.mjs napcat config|start|autologin|webui
node scripts/ops.mjs selftest --json          # 不需要外部依赖的自检（node 版本、目录、依赖）
```

输出长这样（`doctor --json`）：

```json
{
  "schema": 1,
  "ok": false,
  "action": "doctor",
  "platform": { "os": "linux", "systemd": true, "container": true, "elevated": false },
  "findings": [
    { "level": "error", "code": "ONEBOT_UNREACHABLE",
      "message": "ws://127.0.0.1:3001 连不上",
      "fix": "确认 napcat 容器在跑、端口映射到 3001",
      "requires": "human" }
  ],
  "steps": [
    { "id": "fix-ONEBOT_UNREACHABLE", "status": "planned", "requires": "human",
      "command": "docker ps", "note": "先看 napcat 容器" }
  ]
}
```

**三条纪律**：

- **退出码是接口的一部分**：`0` 全部通过；`1` 有 error 级 findings；`2` 需要人工或提权；
  `3` 脚本自身出错。agent 只看 `findings[].level` 决定要不要找用户。
- **`--apply` 默认关**：写 `cwd` 外的步骤（systemd unit、计划任务、NapCat 配置、profile）
  一律带 `requires: human | root`，不带 `--apply` 只打印计划；带 `--apply` 也只执行
  `workspace` 那批，剩下的把命令原样打给你。**不假装能重启桌面版**：Windows 上那一项就是
  一句「请重启桌面版」和 `requires: human`，比静默失败诚实。
- **幂等**：重复执行不重复写；写前备份（沿用 `napcat.js` / `desktop.js` 的备份约定）。

`node scripts/napcat-setup.mjs` **保留为兼容入口**（肌肉记忆），内部走同一批计划函数。
`docs/ops.md` 是给 agent 的排查配方（连不上、不回复、人设没生效、摘要没跑、key 没轮换、
Windows 装了不加载、计划任务没起来、日志在哪）。

## 本机开发

插件以 `link:` 方式装进 profile，源码就在当前目录。裸跑 `node --test test/` 时，Node 需要
能从本目录解析插件 import 的那三个 `@deepseek-ai/*` 包（`schemastery` / `dsh-tools` /
`dsh-llm`）。Linux/macOS 上那是一条第 0 代的软链接：

```
node_modules -> <dsh 安装目录>/node_modules
```

**Windows 上这条路走不通**：桌面版把这三个包放在 `resources/app.asar/dsh/node_modules`
（asar 归档里的虚拟目录，没有对应的真实目录可以软链），而 Windows 建软链/junction 在受限
令牌下会被拒。所以仓库里改用「按依赖闭包拷贝真实文件」的脚本：

```powershell
node scripts\dev-node-modules.mjs --from D:\deepseek-harness   # DSH 源码 checkout
node --test test\
```

它从一份 DSH 源码 checkout 出发，解析出那三个包真正 import 到的每一个包（十几二十个），
平铺拷进本仓库的 `node_modules/`（已在 `.gitignore` 里）。**它只服务开发与测试**：插件运行时
用的是 DSH 自己的解析（靠 `package.json` 里的 `peerDependencies` 声明，见
[Windows 桌面版](#windows-桌面版napcatshell)）。

> **发布包里跑不了测试**，要先铺依赖：zip 走 `git archive`，只带被 git 跟踪的文件，所以
> `node_modules/` 不在里面 —— 而 `bridge` / `client` / `perceptual` / `settings` / `util`
> 这五个测试文件都 import `index.js`，会连带 import 那三个 `@deepseek-ai/*` peer 包。
> 症状是整文件级失败（`✖ test\util.test.mjs`，只有 91 条被收集、5 条模块解析失败）。
> 想验就把上面那条 `dev-node-modules.mjs` 跑一次 —— 但它需要一份 **DSH 源码 checkout**，
> 只拿到 zip、没做过开发的人跑不了。**这不代表发布包坏了**：插件本身不需要自带
> `node_modules`（那三个 peer 由宿主运行时提供）。

> 在 DSH 自己的沙箱里跑测试时，`node --test` 会派生子进程并捕获输出，而沙箱不允许管道
> （`spawn EPERM`）。同一个套件用同进程模式跑即可：`node --test --experimental-test-isolation=none "test/*.test.mjs"`。
>
> 基线是 **491 条全过、0 跳过**（0.2.0 删掉 JM 之后，原先那 13 条「沙箱里跳过」的探针也随
> 之消失 —— 现在没有一条用例需要真的 `spawn` 外部进程）。原有的偶发规律仍在：全量同进程
> 连跑时偶尔红一条、且每次不同（`until` 轮询与真实计时的竞态），单独跑永远绿，重跑确认即可，
> 别为了「让它稳」放宽断言。
>
> 新增的纯函数测试文件：`test/persona.test.mjs`、`test/style.test.mjs`、
> `test/speech-policy.test.mjs`、`test/modalities.test.mjs`、`test/links.test.mjs`、
> `test/interactions.test.mjs`、`test/cognition.test.mjs`、`test/migrate-cognition.test.mjs`、
> `test/ops.test.mjs`。行为层的新用例在 `test/bridge.test.mjs`：气泡计划、标点清洗、
> 插话强制锚点、C 路四条排除、私聊补一句、戳一戳、链接预览、视频封面、语音占位。

### 改完源码必须重启 Harness

Loader 在进程内按 URL 缓存插件模块，**停用/启用插件不会重新加载代码**
（已验证：`set_plugin` 会注销并重新注册工具，但模块仍是第一代；改入口文件名、
`remove_bundle` + `install_bundle` 同样无效）。改了 `index.js` / `config.js` /
`settings.js` / `tools.js` / `onebot.js` 这些模块之后必须重启 `dsh --profile qqbot` 进程：

```bash
# Ctrl-C 后重新执行
dsh --profile qqbot --port 3081 --no-open
```

只有插件 `cordis.patch.yml` 里的配置改动可以热生效，源码改动必须重启。

跟它聊的那个人接着说的话真的会被接住（正文照样是原话，前缀模式下不会被按前缀长度切掉）、
别人插一句不算（窗口跟着「最后跟它说话的那个人」走）、中间有别人说过话这段一对一就断了、
`@别人` 的消息不算接话、`activeMaxTurns` 接够了就要求重新 @、窗口过期同理（默认 1 分钟）；
**多人搭话**：群里几个人说够 `activeGroupLines` 条、够 `activeGroupSpeakers` 个人之后，
没被 @ 的陌生人说话也会被接住、之后换个人说话照样算、同一个人自己刷屏（人数不够）不算、
搭话状态里攒批窗口真的按 `activeGroupBatchScale` 变长（到点前不投出去）、
`activeFollow: false` 时这套同样不生效、`/reset` 把群聊热度一起清掉；**搭话抽卡**：
够资格也未必接（起始概率 0 时真的一句都不进模型）、连丢一条之后概率涨上来才接、抽中之后
累计归零、被明确 @ 到也归零、多人搭话里换个人接话同样按那一次掷中的概率走、这段对话凉掉
之后累计不跨对话（不把上一场攒的保底留到下一场），以及概率曲线的纯函数边界（起始 + 每步
累加、封顶、上限配得比起始小、NaN 一律不接）；以及「补一句」：
回完之后对方安静一小会儿它真的补一句（私聊与群聊各一条通路，提醒里点明「你已经回过话」）、
判成 `SKIP` 一个字都不发、没有 `proactive` 总开关就不补、群里中间有人插话不补、
对方再说一句会把挂着的补一句作废（不会攒出一堆）、`activeChimeDailyMax` 用完了不再补、
`/reset` 把「还聊着」与挂着的补一句一起忘掉、以及「`/reset` 换成新一轮的 Session id
而旧会话留在磁盘上」「重开进程后仍然停在同一轮」「只有 `resetUsers` 里的人能重置，别人
连会话都开不出来」，外加 `mentionsOthers` 的纯函数用例。
窗口里接上的那句**不会**触发 `/reset` 这类旁路（它只是闲聊，指令要明确叫它）。

## 安全提醒

- QQ 消息是**不可信输入**。默认 `approvalPolicy: never`，需要审批的操作
  会被直接拒绝，避免机器人被群里的人指使去执行危险命令。
- 默认只在被 @ 时响应群消息；如果要放开，建议同时用 `allowGroups`
  限定群范围。
- `proactive: true` 会让机器人**主动**给群里发消息（私聊不会）。它与 @/前缀触发无关，
  也就是说它会绕开「只在被叫到时才说话」这条默认约束 —— 所以它默认是关的，而且只对
  已经聊过的群生效。真要开就配好 `allowGroups`、`proactiveFromHour` /
  `proactiveToHour` 与 `proactiveDailyMax`。
- `activeFollow: true` 会让它在群里回应**没有 @ 它**的消息：既包括「正在跟它聊的那个人、
  且中间没人插话、且没 @ 别人」的一对一接话，也包括**多人搭话** —— 群里一段时间里够条数、
  够人数地聊起来之后，谁接话都算数（直到大家停下来）。这一步同样是放松「群里只在被叫到才
  说话」这条默认约定，所以默认关；不放心就别开，或者把 `activeMaxTurns` 调小、
  把 `activeGroupLines` 调高或设成 `0` 关掉多人搭话。
  另外，这些「免 @ 搭话」还要过 `activeTalkChance` 一族的**抽卡**才会真的开口（默认 5% 起、
  每条没抽中 +10%、上限 80%）—— 它是让频率更像真人的那一层，不是安全边界：真想收紧就照上
  面那样关掉资格，或者把 `activeTalkChance` / `activeTalkChanceStep` 都设成 `0`。
- **API key 轮换（`apiKeyRotate`）会改写全局凭据文件** `$DSH_HOME/.credentials.yaml`：
  它默认开着，但只在 `apiKeyFile` 里存在「另一个探测通过的 key」时才会真的写。也就是说
  **谁能在 `cwd` 里放这个文件，谁就能决定 bot 用哪把 key** —— 池子文件别放在别人写得到
  的地方，也不要把它提交进 git（`data/` 已经在 `.gitignore` 里）。它只能改 `apiKeyRef`
  指定的那一个引用，不会动凭据文件里的其它记录（浏览器会话等由凭据层自己维护）。
  不想要这个行为就把 `apiKeyRotate` 设成 `false`。
- Agent 跑在 `cwd` 指定的目录里，受沙箱策略约束。
- **私聊补一句（`privateAfterthought`，默认开）是对「主动消息只有一个总开关」的一次语义例外**：
  群聊的主动消息归 `proactive`，而私聊的补一句是「刚聊完再看有没有想补充的」，有自己的开关、
  概率与每日上限。它仍然是「主动给真人发消息」，所以五道闸门一条不少（只在正常回复后、对方
  没接话、一次一条、有日上限、可 SKIP）。不想让它开口就设 `privateAfterthought: false`。
- **`linkPreview` 默认关**：打开它等于替群里任何人访问任意 URL（暴露本机出口 IP、留下一次可
  被用来探测的请求）。它带完整的 SSRF 防护（私有网段、localhost、数值变形的 IPv4、每一跳
  重定向重新校验、大小与超时上限），但**默认仍然关着** —— 卡片消息不联网就能解析，已经够用。
  `linkAllowPrivateHosts: true` 只该在自建 wiki 这类明确内网需求下开。
- **戳一戳的回应是「QQ 消息驱动的动作」**：`pokeMode: poke` 会让群里任何人戳它一下、它就戳
  回去一下。防循环靠 `pokeCooldownMs`（每个会话 30 秒只回一次）与 `pokeDailyMax`；回戳只打给
  戳它的人，**不会**打给第三人。受不了就设 `pokeMode: ignore` 或 `pokeReply: false`。
- **唯一一个能让 QQ 会话写磁盘的工具是 `qq_save_sticker`**（`allowTools` 里可以去掉它）：
  它只往 `stickerDir` 里写一个文件名被洗成单层的图片，字节还要先过魔数与大小校验，
  张数受 `stickerMaxFiles` 限制，同名不覆盖。除此之外 QQ 会话没有 write / edit / bash ——
  这是「群里谁都能让它存一张图」与「工作区不能被群里的人写坏」之间的那条线，别随手挪。
